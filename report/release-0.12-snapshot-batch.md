# 0.12 权威快照批量组装（2026-09-10）

本阶段将同一发送步内的公共实体状态和玩家公开信息复用。**在隔离组装测量中，平均 CPU 时间由 19.097 ms 降到 10.298 ms，降低 46.1%。** 未改变快照结构、战争迷雾规则、单人私有信息、15 Hz 发送频率或网络协议。该数字不代表整局 FPS。

## 实现与正确性

`MatchReplication.tick()` 先确定本逻辑步要发送的 3 或 4 名远端真人，再一次性调用 `build_snapshots`。权威实体注册表只遍历一次，某个实体只要被任一收件人看见，其位置、生命值和 native AnimationPlayer 姿态只采样一次。每个玩家的公开字典只建立一次。

每个收件人的实体与矿脉可见性仍分别计算；订单、Shift 计划、训练／研究队列、集结点与实际支付费用只追加到该实体所有者的独立字典。经济与科技私有信息同样独立。公共字典不会被添加任何人的私有字段。

数据仅在一次同步发送调用内共享，编码方按只读使用。**没有跨步缓存，也不持有实体 Node。** 单独调用 `build_snapshot` 每次重新采样，因此同一个 tick 内发生的死亡、改令、金币变化和视野变动也不会读到旧值。

新建临时回归 **912 项检查通过、0 失败**（其中核心功能 800 项，其余检查实际编码结果非空）：

- 7 个收件人逐个与修改前实现比较，JSON 文本和最终压缩包逐字节相同，并通过真实客户端快照 schema 检查。
- 32 个单位／建筑的公共状态在 7 人发送批次只采样 32 次；空发送批次不采样任何实体。
- 自己、同盟、敌人的订单／经济／训练／集结点严格隔离，敌方军队、建筑和中立矿脉按接收者视野过滤。
- 同 tick 订单、金币、死亡与迷雾隐藏／重见立即反映在新快照，旧快照不被后续权威状态修改。
- 60 个逻辑步内，7 名远端玩家各收到 30 次快照；重复调用同 tick 不多发包，房主不发给自己；转 Bot 后停止发送，恢复真人后继续。

## 同条件 CPU 与编码对照

官方 Godot 4.6.3 无头进程，使用实际可编辑单位场景：500 单位、8 建筑、2 矿脉，全视野。每步收件人数按 4／3 交替，两个方案按 AB／BA 交替；前 4 轮预热后各记录 12 个样本。场景单位静止、动画为 MANUAL，额外单位主要为同坐标的剑士，用于隔离组装与既有 codec，不能代表移动战场的压缩率或动画成本。用户编辑器与正式游戏保留运行，没有与另一个性能验证进程并行。

| 每个发送步 | 修改前平均 | 批量组装平均 |
|---|---:|---:|
| 组装（4／3 收件人混合） | 19.097 ms | 10.298 ms |
| 组装（4 收件人） | 21.665 ms | 11.122 ms |
| 组装（3 收件人） | 16.529 ms | 9.474 ms |
| 实际 JSON／ZSTD 编码总计 | 15.969 ms | 15.934 ms |

编码仍然昂贵，本次没有改变编码器或 wire 格式，不能把编码差异当优化收益；该组当时没有单独测量 JSON 和压缩各自耗时；下文另有编码分解。动态战斗、屏外动画同步、七名真人真实网络和整局帧率需要各自的后续验证。

原始样本、每步人数与执行前后相同的源码 SHA256 见 [JSON 报告](release-0.12-snapshot-batch.json)。首次两次 helper 因新 worktree 缺少 Godot 类缓存直接解析退出；补入既有导入缓存后的 `measure2` 才是有效数据，失败尝试原日志未覆盖。


## 屏外 native 动画同步的补充分解

另用临时计时脚本副本验证 500 个真实混编模型全部处于屏外动画休眠（六种原模型，非 MANUAL）。两个实现分别在连续逻辑步采样，按 ABBA 交替，避免第二个方案享受第一个方案已经推进动画的同帧偏差。16 步剔除前 4 步后，各取 6 个样本。这是有计时开销的局部诊断，与上表冻结动画场景不可混成同一组对照。

| 每个发送步 | 原方案 | 批量方案 |
|---|---:|---:|
| 快照组装总计 | 29.980 ms | 18.973 ms |
| synchronize_animation 调用 | 1750 次 | 500 次 |
| synchronize_animation 包含 native advance 的累计耗时 | 9.644 ms | 7.199 ms |
| 既有 JSON／ZSTD 编码总计 | 16.802 ms | 17.029 ms |

动画同步仍是明确成本。批量组装减少重复调用，但本步需要采样的 500 个模型依然要实际推进原生动画，约 7.20 ms 未被本改动消除。这里没有更改动画时钟、出手关键帧或屏外姿态规则；以后若改为只导出动画 phase、延迟 pose 采样，需要单独验证武器 socket、攻击出手、客户端插值与重新入屏。

计时 scope 有嵌套：公共实体状态计时包含动画计时，不能相加；旧实现的实体计时还包含 owner 私有字段，新实现私有字段在另一个函数，因此二者实体子项不能直接当作同一 exclusive-time 指标。该组未单拆 JSON 与压缩；下文为独立新场景分解。

有效补充运行 anim2 正常退出、stderr 为空；前一条 anim1 仅因临时夹具的 typed Array 三目赋值错误而中止，修复夹具后重跑，产品源未改。所有失败尝试均使用独立标签保留原始日志。本组最终辅助进程已退出，CIM 核实只保留用户编辑器与正式游戏。


## 限时尝试：只读取屏外动画 phase

本轮尚未找到简洁、原生且完全等价的替代方案，**0.12 保留当前同步行为，UnitVisual 没有因此修改**。官方接口说明，seek 的 update=false 延迟属性更新，而且 seek 到末尾不触发正常结束；advance 才处理完整播放推进。[AnimationPlayer 官方文档](https://docs.godotengine.org/en/4.6/classes/class_animationplayer.html)

六种实际原模型的短 oracle 观察一致：seek 到末尾后 is_playing 仍为 true，advance 后才变为 false；seek 不更新节点时武器 socket 原地不动，补上实际 pose 采样后，测得误差从农民的 0.021 到投石车的 1.890 世界单位。直接把原生时钟 seek 当作当前同步替代会保留旧出手位置。

必须纠正一条未复现推断：初读引擎源码曾怀疑首次 advance 会吞掉 delta；实际 UnitVisual.strike 后补进 0.1 秒，六种模型均得到 0.1 秒，所以该推断没有作为否决结论。完整 seek／pause／循环／复见／攻击关键帧等价性仍需独立验证；只读推算进度与实际待更新 pose 时间也需明确分离。本轮没有完成这样的新时钟设计，不提交未经验证的替换。

另补充真实 RelayClient.send_event 与 MatchReplication 队列协作回归 8 项通过：墙钟限流返回 ERR_BUSY 时保留非装饰事件，不推进 visual tick，重复尝试不重复发包；实际等待 65 ms 后成功移除一次，过期事件仍按原规则丢弃。只替换最底层包接收器记录调用，没有把它称作 DTLS 实测。第一版夹具将 SceneTree timer 误当墙钟等待，独立失败日志保留；改为 Time.get_ticks_msec 后重跑通过。


## 发行前补测：JSON、UTF8 与 ZSTD 分时

新建临时夹具，使用实际六类 500 模型，分布位置、朝向和攻击 phase；静止 MANUAL 动画用于隔离编码。每个发送步按 4／3 收件人交替，总 8 步、剔除头 2 步，下表为余下 6 步均值。28 个手动拆分计时后的包与正式 `encode_snapshot` 包逐字节相同，失败为 0。

| 每个发送步的独立 scope | 平均时间 |
|---|---:|
| 快照批量组装 | 10.275 ms |
| 外层 envelope 字典 | 0.008 ms |
| JSON.stringify | **18.589 ms** |
| UTF8 编码 | 0.284 ms |
| ZSTD 压缩 | 0.440 ms |
| ACN1 头部与 append | 0.021 ms |
| 另行执行的完整正式 encoder | 19.489 ms |

JSON 占明确拆开的编码子项约 **96.1%**，因此当前主要剩余编码成本是 JSON 序列化，不是压缩。每步平均 JSON 原文约 379,431 字节，压缩后包合计约 29,336 字节。完整 encoder 是额外重新执行一次的对照计时，不能与前面子项相加。该小样本不代表真实七 Game 的 TPS、带宽或渲染帧率，也不能直接与更早同坐标夹具做收益比较。

codec1 进程退出码 0、stderr 0；执行前与稍后核查的协议/复制脚本 SHA256 相同，结果归档在 JSON 的 `codec_split_diagnostic`。随后新建了实际发行包可用的可选 500 单位联网压力分支：452 军事与 48 农民、已升级合法人口、HP×100、Bot 策略停用但原生单位战斗与完整快照保持。该分支只完成解析校验，真实运行结果由正式发行验收另行报告。它分别输出 30TPS／15Hz 目标、命令与命中、原生 ENet 字节计数，不把“不断线”表述为“满负载流畅”。


## 第二阶段：公共 JSON 只编码一次

保留 `build_snapshots` 作为唯一状态构建入口。每个短期发送批次内，将每个单位、建筑、玩家的公共字典交给原生 `JSON.stringify` 一次并复用结果；所属玩家的完整私有版本独立编码，战争迷雾仍逐收件人编码。没有跨 tick 缓存，没有另一套游戏状态 builder，没有占位字符串替换。既有 Dictionary API 仍可用，新旧发送入口共用身份、收件人、50 ms 频率与序号检查；UTF8 大小上限、ZSTD、ACN1 和接收端完整校验保持一致。

全新临时回归 **4551 项通过**，包括六类实际模型、1/3/7 收件人及倒序、特殊字符玩家名、完整 JSON 文本与字段顺序、压缩包逐字节等价、真实 decoded 树及 schema、所有权/金钱/队列/科研/迷雾隔离、同 tick 改令、死亡、重新发现、Bot/真人恢复、相位和重复 tick。另以真实 localhost ENet 双端验证发送成功、原/新 API 共享限频、失败不消耗序号、非法身份、空位/Bot、空 JSON、超长 UTF8 与 epoch/序号界限。没有将 localhost ENet 称作公网 DTLS 对战。

500 个分布位置/朝向/动画 phase 的六类 MANUAL 原生模型，4/3 收件人交替，同一次静态场景内 AB/BA 顺序执行；4 个预热步后，每方案 8 个样本：

| 每个发送步 | 原完整编码 | 共享公共 JSON |
|---|---:|---:|
| 相同快照组装 | 9.590 ms | 9.611 ms |
| 公共 JSON 批次编码 | — | 10.519 ms |
| 剩余完整编码/原生封装 | 19.248 ms | 0.988 ms |
| **组装 + 完整 wire 编码** | **28.839 ms** | **21.117 ms** |

编码部分下降约 **40.2%**，包含组装的总成本下降约 **26.8%**；两者平均 wire 字节均为 30,620.5。该结果不包括真实移动、RVO、屏外动画追赶、七个 Game 共享 CPU 或公网传输。屏外原生动画约 7 ms 的已知成本仍可能使真实房主预算不足，不能据此宣称 500 联机已经稳定 30TPS。本阶段保持原 30TPS 分相位发包时机，下一阶段的发送调度需独立验证。

measure1 退出码 0、stderr 空；三个产品文件运行前后 SHA256 一致。数据和源码指纹已归档 JSON 的 `shared_json_encoding`，辅助进程 PID42880 已退出并核实。

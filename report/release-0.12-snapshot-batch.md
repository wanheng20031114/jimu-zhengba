# 0.12 权威快照批量组装（2026-09-10）

本阶段将同一发送步内的公共实体状态和玩家公开信息复用。**在隔离组装测量中，平均 CPU 时间由 19.097 ms 降到 10.298 ms，降低 46.1%。** 未改变快照结构、战争迷雾规则、单人私有信息、15 Hz 发送频率或网络协议。该数字不代表整局 FPS。

## 实现与正确性

`MatchReplication.tick()` 先确定本逻辑步要发送的 3 或 4 名远端真人，再一次性调用 `build_snapshots`。权威实体注册表只遍历一次，某个实体只要被任一收件人看见，其位置、生命值和 native AnimationPlayer 姿态只采样一次。每个玩家的公开字典只建立一次。

每个收件人的实体与矿脉可见性仍分别计算；订单、Shift 计划、训练／研究队列、集结点与实际支付费用只追加到该实体所有者的独立字典。经济与科技私有信息同样独立。公共字典不会被添加任何人的私有字段。

数据仅在一次同步发送调用内共享，编码方按只读使用。**没有跨步缓存，也不持有实体 Node。** 单独调用 `build_snapshot` 每次重新采样，因此同一个 tick 内发生的死亡、改令、金币变化和视野变动也不会读到旧值。

新建临时回归 **912 项检查通过、0 失败**（其中核心功能 800 项，其余检查实际编码结果非空）：

- 7 个收件人逐个与修改前实现比较，JSON 文本和最终压缩包逐字节相同，并通过真实客户端快照 schema 检查。
- 32 个单位／建筑的公共状态在 7 人发送批次只采样 32 次；空发送批次不采样任何实体。
- 自己、同盟、敌人的订单／经济／训练／集结点严格隔离，敌方军队、建筑和中立矿脉按接收者视野过滤。
- 同 tick 订单、金币、死亡与迷雾隐藏／重见立即反映在新快照，旧快照不被后续权威状态修改。
- 60 个逻辑步内，7 名远端玩家各收到 30 次快照；重复调用同 tick 不多发包，房主不发给自己；转 Bot 后停止发送，恢复真人后继续。

## 同条件 CPU 与编码对照

官方 Godot 4.6.3 无头进程，使用实际可编辑单位场景：500 单位、8 建筑、2 矿脉，全视野。每步收件人数按 4／3 交替，两个方案按 AB／BA 交替；前 4 轮预热后各记录 12 个样本。场景单位静止、动画为 MANUAL，额外单位主要为同坐标的剑士，用于隔离组装与既有 codec，不能代表移动战场的压缩率或动画成本。用户编辑器与正式游戏保留运行，没有与另一个性能验证进程并行。

| 每个发送步 | 修改前平均 | 批量组装平均 |
|---|---:|---:|
| 组装（4／3 收件人混合） | 19.097 ms | 10.298 ms |
| 组装（4 收件人） | 21.665 ms | 11.122 ms |
| 组装（3 收件人） | 16.529 ms | 9.474 ms |
| 实际 JSON／ZSTD 编码总计 | 15.969 ms | 15.934 ms |

编码仍然昂贵，本次没有改变编码器或 wire 格式，不能把编码差异当优化收益；没有单独测量 JSON 和压缩各自耗时。动态战斗、屏外动画同步、七名真人真实网络和整局帧率需要各自的后续验证。

原始样本、每步人数与执行前后相同的源码 SHA256 见 [JSON 报告](release-0.12-snapshot-batch.json)。首次两次 helper 因新 worktree 缺少 Godot 类缓存直接解析退出；补入既有导入缓存后的 `measure2` 才是有效数据，失败尝试原日志未覆盖。

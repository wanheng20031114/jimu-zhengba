# 积木争霸 0.10.0 性能复测

**功能流程通过，稳定60FPS和八人满人口性能目标未达到。** 本次数值与新科技没有解决既有导航和模拟追帧瓶颈。

Godot 4.6.3 / RTX 3080 / 1600×900 / Forward+ Vulkan，原生4v4地图、当前模型、阴影、抗锯齿、音效和迷雾。每阶段预热后采样15秒。保留用户编辑器，属于共享工作站测量；不能把两次独立采样的差异直接归因于本次代码。

| 场景 | 平均 FPS | 实际 TPS | 显示 P95 / P99 ms | 逻辑 P95 ms |
| --- | ---: | ---: | ---: | ---: |
| 272 单位 | 74.40 | 30.00 | 42.622 / 44.954 | 13.364 |
| 896 单位 | 1.90 | 15.19 | 546.932 / 547.646 | 50.178 |

272单位为每人24名混编军事单位和10农民，共192军队+80农民；其军事人口按资源计算，骑士已占1人口。896单位为每人100名轻步兵军队和12农民，共800军队+96农民，研究人口与农民扩展后创建。为了稳定人数，压力测试临时放大生命100倍；这不是实际对局的生命值。Bot与自然收入暂停避免持续扩军，镜头位置固定，仍包含真实移动、采矿、攻击和导航；不是八客户端联网渲染测量。

满人口阶段再次出现每个显示帧连续补执行8个逻辑步的现象，逻辑P95超过33.3ms预算。272单位虽平均高于60FPS，显示P95仍超过16.7ms，不能说稳定60FPS。0.9.0曾分别测得81.55与1.94FPS，本轮74.40与1.90；此前的极限瓶颈依然存在。

恢复科技另做896原生伤兵的专门微基准：已研究时整批回调平均1.031ms、P95 1.107ms、P99 1.850ms；未研究时平均0.570ms；启用科技平均增量0.461ms。这不是对旧版本没有该回调的直接增量，也不是单个单位成本。全体单位在600个30TPS步内准确恢复20点生命。详见[科技验收](special-upgrades-0.10.0.md)。

塔阶梯报价为计数直接索引，单位回复复用已有逻辑步，炮射程读取所属玩家科技，均未引入全局搜索或逐单位Timer。整体模拟仍须遍历活跃单位：每单位O(1)并不意味着整场O(1)，导航、避让、物理查询、雾区与快照构建是其他成本。

本轮896单位+160建筑的快照编码检查：压缩后8422字节，解码后275415字节，仍在原协议边界内；这是构造快照编码检查，不能冒充真实每秒公网流量。八客户端4v4另通过4%丢包、延迟与乱序的真实ENet检查。

下一阶段有证据支持的优化方向：减少相同目标的重复重寻路、以目标移动事件和路径失效事件触发路径更新、共享小队接敌路径、按空间分区限制查询；应保持权威模拟与玩家命令响应，不以跳过伤害或客户端各自模拟掩盖延迟。此处列的是后续方向，并未宣称已经实施。

原始结果见[性能JSON](performance-0.10.0.json)，包含阶段耗时分布、进程核实及采样条件。基准进程已退出，仅保留用户原有编辑器。

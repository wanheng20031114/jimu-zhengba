# 0.11.0 原生阶段耗时诊断

本记录用于定位一次 **896 单位实验快照**的 CPU 墙钟耗时，不能作为最终发布版 FPS。采样使用 Godot 4.6.3 的 MSVC 临时优化引擎，带有原生分段计时，并包含后来已经撤回的 **10 Hz 战斗决策实验**。正式发行引擎使用不同的编译工具链，绝对性能不能直接比较。

只统计日志 `JIMU_MEASURE_BEGIN` 与 `JIMU_MEASURE_END` 之间的完整报告窗口：丢弃 BEGIN 后首个与预热相交的窗口，并排除 END 之后含收尾工作的窗口。最终保留 **5 个窗口、11.24528 秒、240 个物理步、30 个渲染帧**。各阶段由 `累计微秒 ÷ 实际调用次数 ÷ 1000` 求均值，不使用 Godot 每秒更新的物理峰值缓存。全部 26 个阶段的原始整数统计和筛选依据保存在 [脱敏 JSON](performance-native-0.11.0.json)。

| 阶段 | 每物理步平均耗时 | 包含关系 |
|---|---:|---|
| 完整原生物理步 | **42.211 ms** | 以下物理阶段的总范围 |
| 完整 SceneTree 物理处理 | 31.272 ms | 包含下一行以及变换、计时器、消息等处理 |
| 其中：SceneTree 节点物理回调 | **30.465 ms** | 原生 `_process(true)`，含脚本、原生节点回调和分组调度 |
| Navigation3D | **8.260 ms** | 地图同步、RVO 和安全速度回调，包含移动代码 |
| Jolt 服务器步进 | **0.563 ms** | `PhysicsServer3D::end_sync()` 与 `step()` |
| 物理步准备 | 0.873 ms | 插值准备及需要的变换刷新 |
| 物理步结束 | 1.227 ms | 变换刷新及插值维护 |

这些是父子包含时间，不能把完整物理步或完整 SceneTree 与其子阶段重复相加。SceneTree 计时器/Tween 后的变换刷新平均 **0.776 ms**，已包含在 31.272 ms 中。Navigation3D 的 8.260 ms 也不能被称作“纯 RVO 计算”，而角色的 `move_and_slide()` 不属于表中的 Jolt 服务器步进。

这次实验的主要耗时集中在 SceneTree 节点物理回调，Jolt 服务器步进只占很小一部分。每个渲染帧在这组窗口中都执行了 8 个物理追帧步骤。另按渲染帧统计，`MainLoop::process()` 平均 **26.054 ms**、渲染提交阶段平均 **10.860 ms**、完整帧工作平均 **374.806 ms**；这些是主线程墙钟时间，不能当作 GPU 的独立运行时间。

现有 Begin/End 优先级标记得到 **28.501 ms** 的回调均值，统计了完整测量期 **15.332009 秒内的 328 步**；本报告的原生回调均值 **30.465 ms** 只覆盖中间 240 步。五个保留窗口的回调均值分别为 28.752、30.389、30.965、30.061、32.158 ms，说明裁剪区间会改变均值。原生 `_process(true)` 还包括标记范围外的分组、排序、队列刷新和调度。由于没有相同逐步样本的配对数据，不能把两种均值的差额全部归因于某个原生函数，也不应使用末窗或跨 END 的尾窗把整体均值概括成“33 ms”。这些范围由 [Godot 4.6.3 SceneTree 源码](https://github.com/godotengine/godot/blob/4.6.3-stable/scene/main/scene_tree.cpp)核实。

该场景为 4v4，每位玩家 50 名剑士、50 名弓箭手和 12 名农民，共 896 个单位。基准将生命乘以 100 以维持人口，暂停 Bot 与自然收入，保留战斗、采矿、导航和场景表现，未运行网络客户端。分辨率为 1600×900，Forward+/Vulkan，关闭垂直同步和帧率上限。基准原有 31 项检查全部通过。

原始记录只保留窗口内的累计值、次数和最大单次值，无法据此计算逐物理步 P95/P99。本归档未增加运行测试，也没有据此证明最终版本达到了帧率目标。原生诊断引擎本身不会发布。

# 0.12 最新状态分散发送候选

北京时间 2026-09-11 00:27。相关[本地契约数据与哈希](release-0.12-pacing.json)、[原生缓冲丢尾包复现](release-0.12-udp-buffer.md)。

候选把同批六／七个收件人的发送拆到连续显示帧，并在真实 native 入队前按编码字节限制突发。本地小契约 **31/31** 通过；**尚未完成真实七人 500 单位公网验收，不据此宣布卡顿解决**。

## 实现

- `MatchReplication` 继续按 15 Hz 墙钟构建一次共享公共 JSON 批。每个 owner 只保留一份不可变的待发 JSON，新批替换旧态，不保留历史追赶队列；也不重复执行过去物理 tick 的网络发布。
- 持久轮转游标每个真实 `Engine.get_process_frames()` 机会最多处理 **3 个收件者**。每人已有的 50 ms 发送门槛保留。快照后发送该人的表现批，再逐人 flush，减少相同原生序号的跨频道消息积压在同一个发送列表里。
- `RelayClient` 在完整 ACN1 编码后检查字节，所有快照、表现共享每显示帧 **48 KiB** 预算；控制、通知、心跳、暂停、结算不受 bulk 配额阻塞，但其已发送编码字节会减少当帧 bulk 余量。重复调用 publish／flush 不能刷新同一显示帧的配额。
- 被剩余字节预算挡住的 owner 保留下一帧第一个机会；因本人的 50 ms 门槛 BUSY 则继续轮转。这个区别避免尺寸较大的后排 owner 每次都排在已用预算后面，永远无法发送。
- 表现沿用有界队列、时间戳和过期规则；BUSY 不移除事件、不推进快照序号或发送时间。断线、连接重建、start／恢复、暂停、离房、结算同步清除尚未入原生队列的旧快照与表现；已进入 ENet 的数据无法在项目层撤回。
- **协议合法、但单包编码已超过 48 KiB 的快照不新增硬拒绝。** 它只在当帧还没有其他 bulk 时独占一次，沿用原生分片，并每 owner 有界记录一次诊断；随后的 bulk 延后。此例外不保证解决超过内部缓冲能力的极端大包，不能把它当作可靠分块协议。没有截断实体或泄露其他玩家私有数据，没有改 wire、服务器或 ENet throttle。

48 KiB 计量是应用编码字节，给典型 500 单位约 12 KiB 的单人快照留出分批空间；它不是包括任意可靠重传、DTLS 和路径 MTU 的完整安全证明。低显示帧率时实际可发送频率仍受处理机会限制；15 Hz 是构建／上限节奏，不保证在任何 CPU 负载下每名玩家都收到 15 Hz。

## 新夹具的验证边界

使用生产 `RelayClient`、`MatchReplication` 调度与共享 JSON 入口，仅替换世界状态构建为带接收者私有标记和不可压缩噪声的 primitive 字典。一个 Windows Godot **4.7.2** 无头进程内运行两个真实 ENet＋DTLS 端点；没有加载军队、连接公网或运行渲染基准。

三帧实际编码发送量分别为 **38,511／38,515／37,523 B**，9 份已入队快照在原生 DTLS 接收端 **9/9 到达**。第二帧继续轮转到 owner **4、5、6**，收到替换后的最新 tick 及各自私有标记；重复同帧调用没有重发或重复构建。另覆盖控制已用字节挤占 bulk、结算优先、BUSY 保留、暂停／断线清理和大包后排不饥饿。

合法大包实测编码 **61,708 B**，检查的是它被独占放行、阻止同帧其他 bulk、控制仍可发送；该段底层使用捕获端，**没有声称大包穿过原生环形缓冲后必达**。

首轮夹具同时用了 4.6.3 的本地 DTLS 服务端，退出时遇到已知服务器析构 mutex 错误；还误把 `process_frame` 信号当作帧计数已递增。原记录保留，最终改为等待实际帧号变化，并用与线上服务相同版本的 4.7.2 复核。生产逻辑没有为迁就这些夹具错误放松预算。真实 4.6.3 发布客户端与 4.7.2 中继的七人压力验证由后续验收处理。

最终辅助进程正常退出、标准错误为空，按新目录匹配进程命令核实无残留。临时文件留在 `.local/release-0.12-pacing-tests`，由主任务统一清理；本阶段未部署或重启任何服务器。

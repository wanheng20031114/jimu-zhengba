# 积木争霸 0.9.0：八人模式性能审查

本审查区分已经测得的现象、代码中可以确认的工作量，以及尚未实施的建议。地图、房间人数和网络容量验证通过，并不代表八人满人口可以流畅运行。本轮没有修改基础模拟频率、攻击动画或原生避让算法。

## 已有测量说明了什么

依据 [0.8.2 原始验收 JSON](../docs/release-0.8.2-validation.json) 的 `performance` 字段，旧版使用 RTX 3080 / i9-10900KF、Forward+、1600×900、30 TPS，同一组原生地图和单位进行 15 秒采样：

| 指标 | 204 单位 | 672 单位 |
| --- | ---: | ---: |
| 显示帧数 | 1,151 | 37 |
| 实际逻辑步数 | 450 | 296 |
| 每显示帧对应逻辑步数 | 0.391 | **8.000** |
| 平均 FPS / 实际 TPS | 76.71 / 29.99 | 2.42 / 19.40 |
| 单步 SceneTree 逻辑均值 / P95 | 9.19 / 12.35 ms | **31.62 / 38.91 ms** |
| 单步寻路查询均值 / P95 | 0.91 / 2.21 ms | **6.97 / 9.28 ms** |
| 单步寻路查询次数 P95 | 5 | **24** |
| 引擎 Navigation 监视器 P95 | 2.39 ms | 8.07 ms |
| 画面内可见单位，开始→结束 | 150→153 | 488→594 |
| 绘制调用均值 | 823 | 1,155 |
| 引擎统计绘制图元均值 | 134 万 | 321 万 |

672 单位样本恰好每显示帧执行 8 个物理步，已达到 Godot 默认的追赶步数上限；同时，单步逻辑 P95 超出 30 TPS 对应的 33.3 ms 预算。**固定步积压是已被数据支持的主要问题之一，不能把 2.42 FPS 直接解释为单纯 GPU 绘制耗时。** Godot 文档说明该上限用于限制昂贵物理不断触发额外追赶；提高上限会允许每显示帧执行更多模拟，不会让一次模拟变便宜。[Godot Engine：物理步上限](https://docs.godotengine.org/en/4.6/classes/class_engine.html#class-engine-property-max-physics-steps-per-frame)

上述渲染间隔为墙钟时间，并非 GPU 时间戳。引擎性能监视器数值带缓存，不能把 Navigation、SceneTree 逻辑、物理监视器直接相加；37 帧的 P99 也只是短样本估计。旧版样本关闭了 Bot 和联网，仍出现模拟超时，因此网络优化不能单独解决该旧版瓶颈。

## 随人数扩大的工作与建议

以下全部是**设计建议，尚未实施，也没有宣称收益**。行号对应本次审查时的 0.9.0 源文件。

| 位置 | 已确认的结构 | 可行的下一步 |
| --- | --- | --- |
| `scripts/path_budget.gd:8`、`:114`；`scripts/battle_unit.gd:231` | 寻路每步最多 24 次，控制了次数，但没有控制实际耗时；追击每 0.4～0.55 秒重规划，目标终点变化还会触发查询。旧极限样本查询 P95 已打满 24 次。 | 优先增加“用户新命令 / 常规重规划”的分类计时与等待时间统计，再设计同时限制查询数量和微秒预算的调度；新命令应有保留预算和所有者公平性。预算收紧时继续使用仍有效的旧路径，避免把性能改善换成全军停顿。大队重复目的地可进一步研究共享长程走廊，但这属于独立架构改造。 |
| `scripts/battle_unit.gd:227`、`:268`、`:362`；`scenes/unit.tscn:46` | 原生 RVO 每单位持续参与；邻居上限已经是 10，目标搜索也是带敌对物理层的最多 64 个结果，并不是脚本全场两两扫描。 | 将原生避让、目标搜索、移动碰撞分别计时，避免凭感觉替换成熟原生能力。**不要直接关闭静止士兵的避让**：单位 `collision_mask = 3` 不包含单位层，静止士兵仍须作为其他单位的避让对象，否则可能互相穿过。 |
| `scripts/unit_visual.gd:6`、`:20`；`scripts/fog_of_war.gd:169`；`scripts/network/match_replication.gd:417` | 各单位有 4～11 个独立模型 MeshInstance；弓手 11 个，骑兵 10 个。隐藏实体目前改变可见性，没有同步停止纯表现动画；客户端对全部可见副本逐帧更新姿态。旧极限场景记录了 8,024 个带实例参数的几何对象。 | 先在客户端、屏幕外模型上验证纯走路/待机动画降频或暂停，保留位置插值与权威状态。使用原生可见性通知控制纯表现层，重新进入镜头时按当前状态恢复。攻击计时、射弹生成点及房主发出的动画相位不能随镜头停止。若仍不足，再考虑离线合并不独立运动的部件和远景模型，避免临时降低全部美术质量。 |
| `scripts/skirmish_bot.gd:44`、`:69`、`:111`；`scripts/game.gd:150`、`:1003` | 每个 Bot 每秒决策，初始决策累积器相同；房主在同一步循环全部 Bot。所有者查询目前从场景组筛选，观察还会遍历实体。八名 Bot 容易在同一步集中决策。 | 可先将各 Bot 的决策相位按稳定 owner_id 错开，维持每 Bot 每秒一次，再用登记/死亡事件维护按所有者的实体索引。该改动主要减少尖峰，不能拿它解释关闭 Bot 的旧极限样本。 |
| `scripts/network/match_replication.gd:70`、`:91`、`:118` | 0.9.0 已把接收者分成两个发送相位，并压缩快照；每名普通玩家仍需独立过滤状态，八人时最多给七名远端玩家发送。 | 后续可在一个逻辑步内缓存不可变的公开实体基础状态，然后逐接收者做视野过滤和私有队列附加，减少重复属性提取。不能把某接收者的私有快照缓存给队友，更不能为了省扫描发送隐藏敌人。必须用伪造和迷雾隔离测试验证。 |
| `scripts/fog_of_war.gd:74`、`:92` | 每 0.2 秒为每个联盟重新组织可见格；八人乱战需要八份 96×96 探索网格。圆形视野已经按连续行跨度绘制，避免逐格距离计算。 | 可测量迷雾重算在各人口阶段的独立 P95，并按联盟组织视野来源，减少“每联盟遍历所有实体”。更复杂的增量覆盖计数需专门验证死亡、离开视野、联盟和建筑暴露，不能只缓存坐标后让视野延迟错误。 |

屏幕可见性与模型分组可采用 Godot 原生能力，但可见性通知只应该影响允许降级的表现内容。[VisibleOnScreenNotifier3D](https://docs.godotengine.org/en/4.6/classes/class_visibleonscreennotifier3d.html) 原生导航优化也建议关注地图多边形、查询与避让各自的成本，不能将它们当作一个问题处理。[Godot 导航性能说明](https://docs.godotengine.org/en/4.6/tutorials/navigation/navigation_optimizing_performance.html)

## 0.9.0 八人基准方法

验证工具现支持以下命令，**默认仍为旧的 3v3**：

```powershell
python tools/run_six_player_performance.py --mode 3v3
python tools/run_six_player_performance.py --mode 4v4
```

4v4 使用实际“四旗会战”地图和 z = −60、−20、20、60 四条主线。每席标准阵容为 24 名混合军事单位及 10 农民，共 **272 个单位**；完成两级军队扩编及农民上限科技后，每席 100 轻型军事单位及 12 农民，共 **896 个单位**。农民使用各自独立出生矿和扩张矿，避免测试脚本误占队友的出生矿。

保留 1600×900、Forward+、30 TPS、阴影、原生导航、采矿、真实攻击和特效；关闭 Bot、自然收入固定样本规模，以测试专用百倍生命阻止人口下降。相机仍位于中央，缩放 58，四条战线都会模拟，但不会强制同时挤入画面；报告分别记录画面内可见人数。每阶段预热 6 秒、正式采样 15 秒，报告保持旧字段，单独输出 `artifacts/eight-player-performance-090.json`。

运行器在发现其他验证辅助进程时拒绝开始；对自己启动的进程有超时和退出核实，保留用户正常游戏与编辑器。该样本没有叠加完整联网和 Bot 负载，也不是独占机器测量。任何实际结果应与上述条件一起报告。

## 0.9.0 八人正式采样结果

在其他验证进程全部退出后，按以上命令完成一次正式采样，原始结果未经删减保存于 [eight-player-performance-0.9.0.json](eight-player-performance-0.9.0.json)。全过程约 53.8 秒，退出码 0、无脚本错误、标准/极限阶段人数均保持不变。**这些流程检查通过；稳定 60 FPS 和极限 30 TPS 的性能目标没有通过。**

| 指标 | 272 单位标准混编 | 896 单位极限 |
| --- | ---: | ---: |
| 平均 FPS / 实际 TPS | **81.55 / 29.98** | **1.94 / 15.52** |
| 显示帧 P95 / P99 | **40.946 / 44.172 ms** | **545.735 / 549.317 ms** |
| 单步逻辑均值 / P95 / P99 | 9.291 / 12.007 / 13.448 ms | **41.081 / 49.034 / 51.640 ms** |
| 引擎物理监视器 P95 / P99 | 17.546 / 17.546 ms | 67.822 / 71.670 ms |
| 单步寻路均值 / P95 | 0.149 / 1.117 ms | **11.187 / 13.240 ms** |
| 每逻辑步查询次数，中位 / P95 | 0 / 2 | **24 / 24** |
| 引擎 Navigation 监视器 P95 | 1.596 ms | 8.270 ms |
| 显示帧数 / 实际逻辑步数 | 1,224 / 450 | **30 / 240** |
| 每显示帧对应逻辑步数 | 0.368 | **8.000** |
| 画面内可见单位，开始→结束 | 138→137 | 431→607 |
| 采样期间真实伤害事件 | 2,256 | 1,923 |

标准混编的平均 FPS 高于 60，但 P95 帧耗时超过 40 ms，不能称为稳定 60 FPS。896 人极限场景无法保持 30 TPS，依旧触发每显示帧 8 个逻辑步的追赶上限；这已经影响模拟和操作响应，插值无法补回缺失的实际计算吞吐。现阶段不应推荐八人都升满人口后长期在一个战场集中交战。

新图四条主线、局部拥挤程度和画面内可见人数与旧 3v3 样本不同，不能用两次平均 FPS 作同负载回归结论。896 人阶段仅有 30 个显示帧，P99 是短样本估计；没有独立 GPU 时间戳，也没有同时运行八个联网客户端和 Bot。原始 JSON 的 `ok: true` 只代表运行与数据完整性通过，各阶段的 `frame_p95_under_16ms`、`logic_p95_under_33ms` 保留真实失败状态。

运行器记录自有 Godot 子进程 PID 32288 已退出；结束后额外 CIM 查询仅剩用户正常编辑器 PID 33896，未关闭用户编辑器。测量结果支持先降低每步模拟和寻路的耗时，再分别验证表现动画、绘制、Bot 与网络开销；本轮没有为得到更好数字改变人口、阈值、攻击、原生避让或模拟频率。

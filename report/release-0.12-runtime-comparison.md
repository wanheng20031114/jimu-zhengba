# 0.12 七人联机：运行时边界与突发发送诊断

**发送调度改善了尾部玩家的快照公平性，但 500 单位的联机流畅度尚未达标。** 本报告将编辑器运行时、真正发行运行时和限突发发送的证据分开，避免把无头功能测试误作发行 FPS 成绩。

## 方法与范围

各轮均为七个真实 Game 进程共享一台 Windows 主机，以公网 ENet/DTLS 中继运行 4v4 七真人加一 Bot 房间。500 个合法混编单位使用正常视野与战斗，生命提高以保持压力规模。相同原生发布逻辑加入微秒墙钟统计；没有记录包内容、邀请码或端点。

第一轮使用官方 Godot 编辑器引擎的外部 SceneTree 驱动。后两轮改用原生 `windows_release_x86_64.exe`，把相同测试行为放入常驻 autoload Node，并用空诊断启动场景避免 Lobby 重复绑定。实际 Session 与对局 main/Game 保持产品逻辑。每个发行端均实际验证 `editor=false`、`debug=false`、`template=true`、`release=true`。

## 发布、原生网络与公平性

发行基线 ENet flush 平均 2.170 ms，限突发每收件人单独 flush 平均 0.162 ms；service 均值分别为 0.059 和 0.031 ms。本样本不支持原生 UDP 调用持续阻塞数百毫秒作为主要帧卡顿解释。

限突发稳定段每位收件人的成功快照入队次数为 **79、79、79、80、80、80**。各自压缩快照均值约 **11.02、10.97、10.95、11.81、11.85、11.70 KB**。客户端全程快照总数近似相同，先前最后两位明显少收的现象得到改善。

各 owner 的 `_flush_visual` 调用次数也是 79、79、79、80、80、80，每次约 3.05–3.13 ms。**这只是过滤／发送尝试的调用次数，不证明每个视觉批次都被接受。** 6b91ac1 另有视觉 BUSY 后缺少独立重试的已知缺口，需后续专门回归，不能用这次统计掩盖。

## 42 秒实际观测：release paced1

房主推进 1251 个逻辑步／42.042 秒，即 **29.756 TPS**。500 单位全部存活，发生 9072 次伤害事件。房主原生出站流量约 12,800,357 字节、10,427 UDP 包，约 **304 KB/s**；此数含所有原生传输开销，不等于单纯 JSON 大小。

## 失败证据与仍未解释的边界

发行基线只有 owner 2 自主出现 `native_disconnect`：进程时间 34.230 秒，最近有效接收距当前仅 66 ms，随后收到 `resume_pending`。不是应用层 8 秒无接收超时。测试 runner 在这一端退出失败后终止其余六端；因此其他端缺少结果不能被描述成它们也自行断线。该失败及原始日志保留。

进程 CPU 时间仍明显小于计时墙钟：发行基线房主约 11.859 秒 CPU／37.984 秒辅助进程生命周期；限突发约 14.750 秒／48.343 秒。该统计范围含启动／清理，且 CPU 是所有线程累计。当前没有线程等待或调度跟踪证据，不能猜测为某种锁、系统限额或低频 CPU。应继续区分墙钟和实际 CPU 时间。

Godot Performance 指标仅按“前一窗口最大值”保留，不能从重复缓存值计算逐帧分位数，也不能相减不同峰值。无头运行没有 GPU 呈现验收；诊断包有额外包装和统计开销。后续将 JSON 编码移出主线程的候选必须保持不可变快照、每玩家私有数据和迷雾隔离，另验工作线程发布、重连、销毁以及真实发行运行时表现，不能仅据这张表承诺帧率。

原始数值、范围、哈希和失败状态见同目录 [结构化记录](release-0.12-runtime-comparison.json)。本分析没有修改发行产品或中继，公网验证由父任务运行；其收据记录所有自有辅助进程退出。

## 后续线程化实测：主线程改善，传输体验倒退

`release_threaded1` 使用同一发行模板和同一驱动，产品固定 `eca8ff9`；新增单工作线程 JSON 编码，同时包含视觉事件重复编码消除与独立重试修复。不是单变量 ABBA，不能把每项改进全部归于线程本身。

12–32 秒内完整 19 个窗口为 19.756722 秒：253 帧、593 个物理步。呈现循环约 **12.81 Hz**，帧墙钟 P50 **73.833 ms**、P95 **101.157 ms**、P99 **108.754 ms**，明显改善但仍低于 15 Hz。物理信号跨度 **18.461 ms／步**，与上一轮约 18.192 ms 接近；单位回调约每步 8.678 ms。

| 主线程范围 | 限突发 | 线程化 |
|---|---:|---:|
| Game process／调用 | 51.397 ms | 28.717 ms |
| publish／调用 | 49.413 ms | 27.386 ms |
| 状态采集／批次 | 19.001 ms | 19.381 ms |
| 排队调度／调用 | 11.262 ms | 7.923 ms |
| 单 owner 视觉批次／尝试 | 约 3.1 ms | 约 1.93 ms |

完成的 **253 个 worker job** 均由主线程原生 join 后才归约指标。worker 编码含输入图释放平均 **19.199 ms**、最大 **26.195 ms**；排队平均 **0.0448 ms**、最大 **0.083 ms**。主线程完成 join 平均 **0.0055 ms**、最大 **0.115 ms**。编码在工作线程与主线程工作重叠，不应与主线程时间相加。数据没有显示 worker 排队积压或主线程等待未完成任务。

稳定段捕获／完成 job 数均为 253；六 owner 成功原生快照入队为 **127、127、127、126、126、126**，每人约 6.4 Hz，编码包均值约 11.86–12.04 KB。与上一轮约 4 Hz 入队相比增加。整个压力观察中，房主序号由约 13–15 均衡推进至约 288–289；不能将客户端少收解释为少采集、少启动任务或收件人主线程饥饿。

**网络结果反而恶化：** 房主 1253 逻辑步／42.020 秒，即 29.819 TPS，500 单位存活，发生 10214 次伤害事件，但客户端如下：

| owner | 观察期快照数 | 实收频率 | 最长间隔 |
|---|---:|---:|---:|
| 1 | 74 | 1.762 Hz | 10581 ms |
| 2 | 67 | 1.595 Hz | 11496 ms |
| 3 | 61 | 1.452 Hz | 23147 ms |
| 4 | 80 | 1.904 Hz | 5043 ms |
| 5 | 74 | 1.761 Hz | 7998 ms |
| 6 | 68 | 1.618 Hz | 14299 ms |

房主原生出站 **23,337,560 字节／42.020 秒，约 555 KB/s**，比限突发单线程约 304 KB/s 增加约 82%。六客户端原生接收字节累计约 16.616 MB，但包含不同方向的控制、视觉和重传，不能直接用差值当作快照丢包率。房主 ENet throttle 在健康记录中维持满额；原生“可靠包丢失”统计出现增长，它不是不可靠快照分片的直接丢失率。

ENet flush 仍平均约 0.161 ms、最大 0.298 ms，service 平均约 0.038 ms、最大 0.208 ms，没有持续长阻塞证据。主线程更快后发送量增加、实际快照更少，这将下一步范围指向主机原生入队之后的完整分片接收、中继转发／出口及传输排队。必须结合服务器实际收到／转发计数和链路字节容量确认，当前不能直接宣称某一侧带宽或某段代码已被证实为唯一原因。

这轮 host GetProcessTimes 合计 24.250 CPU 秒／48.328 秒完整生命周期，增加的 worker 执行和更高采集频率会增加 CPU 总量。功能连接检查全部通过，不能掩盖最长 23 秒的状态停滞；本轮不应被描述为整体联机优化成功。

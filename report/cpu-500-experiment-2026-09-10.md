# 积木争霸：500 单位 CPU、显示与导航实验

日期：2026-09-10。实验分支：`codex/cpu-500-experiment-20260910`；基于正式版提交 `a065e2a1fffd138182c39550e4cac19088b86eb0`。实验版本：`0.11.1-cpu-exp.1`。

## 实验边界

本轮目标是提高约 500 个单位同时在场时的可玩性，分别检查显示帧、30 TPS 权威模拟、首次下令与再次改令的响应。896 单位的历史结果属于不同数量、不同场景的样本，不与本轮直接计算提速比例。

修改位于独立 Git 工作树。正式 `builds/windows`、正式版本包及公网 Relay 均不属于本轮发布目标。恢复材料位于 `.local/recovery/cpu-500-20260910`，包含基线源码、开始前的工作区补丁和被修改文件逐字节副本。

## 测量方法与证据边界

- 使用官方 Godot 4.6.3 Windows release 模板、Forward+ / Vulkan、RTX 3080、1600×900。关闭测试窗口 VSync 和帧数上限，保留原来的 30 TPS、八步补帧上限、碰撞、战斗、动画、音效及迷雾。
- 4v4 地图固定种子，八方各 20 剑士、16 弓手、12 骑士、4 投石车、4 加农炮和 6 农民，另外四方各补 1 剑士，共 500 人。农民真实采矿。停止 Bot 战略决策与自然金币计时，以隔离本轮主要变量；不将此测试称为完整八人联网压测。
- 持续负载实验把生命值乘以 100，避免人数因死亡快速下降；伤害和出手仍真实执行。正常生命值的生命周期回归另记。该生命倍数只存在于临时夹具，不进入游戏数值。
- 先静止预热六秒，再由真实命令入口同时向八组部队发令。报告区分最初三秒和第 3～20 秒的持续负载，记录场上人数、屏幕可见人数、移动、攻击、弹丸和伤害量。500 人在场不等于 500 人始终同时显示。
- 帧耗时取显示帧间隔。SceneTree 优先级标记只覆盖节点回调，不能充当完整物理步。`move_and_slide` 位于移动回调内；导航阶段包含 RVO 与安全速度回调，不能与其子项重复相加。
- GPU 时间来自真实根视口计时；它不包含其他视口和 CPU 游戏逻辑。发布版不支持的内存统计返回零时记为不可用，不解释成零占用。
- Godot `Performance.TIME_*` 是约每秒发布的窗口最大值。它不是逐步平均值，不能把重复读取的缓存值计算成逻辑步 P95/P99。
- 初期实验期间用户游戏和编辑器同时运行，保留原进程且明确记录背景。后续曾有另一个任务并行执行碰撞测试，因此那次计时开关开／关对照作废；细分入口只作定位证据。最终对照另行记录进程环境，不能混用受干扰样本宣称净收益。

## 为什么要调查显示结构

CPU 负责提交与更新对象，GPU 负责顶点和像素工作。这不意味着逐个模型零件的节点更新可以忽略。本项目原来一个单位有多个刚性零件节点，两套 AnimationPlayer 修改这些节点，随后产生层级变换、物理插值、可见性和渲染实例同步。

原来网格和不透明材质已共享，Forward+ 可能自动实例化相同网格，所以“网格节点数”不能直接当成“绘制调用数”。本轮需要同时观察 CPU 帧成本和实际调用数，不能仅按减少节点数量宣布成功。

初期同包消融中，持续交战原模型为 36.57 FPS；隐藏单位网格为 70.75 FPS，根视口 GPU 仅从约 2.59 降到 1.93 ms，帧准备 CPU 从约 4.60 降到 0.76 ms。隐藏模型会改变表现和战斗演变，这只是定位证据，不能作为可玩优化成绩。只换剑士的首轮提升也太小，未据此宣布有效。

## 碰撞和寻路结构

单位的物理碰撞掩码只包含地形与建筑；单位之间使用 RVO。RVO 已有 KD-tree 和十邻居上限，当前并不是所有单位两两做完整刚体碰撞。`CharacterBody3D.move_and_slide()` 会进行自己的静态运动查询，因此 Jolt 服务器主步耗时小，不能证明全部碰撞查询也小。

继续验证的两个独立导航候选如下：

1. 共享反向距离场：组命令保留共同目标，后台计算不可变方向场，成员保留自己的编队终点。近距离追击、无有效共享边和最后入位仍使用原生路径。Shift 的未来任务不提前申请场，旧地图版本的工作结果不能发布。
2. 静态空地证书：根据真实静态碰撞形状构建占用格与前缀和，并把安全与不安全结果缓存在单位所在的两米区域中。只有完整扫掠得到安全证明才可省去原生查询；墙边、缓存失效、新建与拆毁期间仍使用原生碰撞。保留单位间 RVO。

当前原生路径已有每逻辑步 24 次的全场预算，单位不是每步都执行 A*。初期持续交战样本中 A* 约为 0.043 ms／步，行军和绕障约为 0.43 ms／步。共享场需要验证的是适用场景的复用和命令响应，不能用它解释所有交战 CPU 开销。

另有两个默认关闭的小候选：省去未使用的路径元数据，以及按地图 RID／物理步缓存地图版本查询。它们的路径等价检查通过，但减少调用次数不自动等于 FPS 提升。

## 实测与最终选择

**当前结论：全军骨骼候选尚未证明整体帧率收益，保持关闭。共享场和静态运动也未凭本轮 500 人数据确认收益。** 结构正确性通过与实际提速是两件事。

机器可读的完整紧凑证据见 [实测 JSON](cpu-500-experiment-2026-09-10.json)：保留冻结 PCK/夹具指纹、分阶段帧分位、回调与寻路开销、人口/移动/可见/出手计数、进度和命令响应；不含地址、凭据、邀请码、命令行或用户进程参数。

本节已完成的测量基于 `a065e2a` 实验源码。正式版 `0.11.0.3` 的群体接触修正随后已合入实验基线 `4caca55`；下面的旧数字不代表新基线成绩。新基线对照需要重新冻结、单独记录。

### 蒙皮 LOD 丢失：已定位并修复

初版转换器读取 `surface_get_arrays()`，创建合并 `ArrayMesh` 时没有传入独立的 `lods` 参数。原模型六类共 48 个零件网格，其中 42 个有 LOD；生成的六个主网格全部没有 LOD。此前千万级顶点检查只覆盖基础几何，不能证明远景几何开销一致。这是已证实的转换缺陷，能够解释增加图元的一部分来源；尚未用修复后的同场对照证明它是全部帧率问题的原因。

修复提交 `e81cb8643691faf3c468ae9e02464679e794e670` 使用原生 `ImporterMesh.from_mesh()` 读取各部件的 LOD 索引及阈值。阈值按绑定姿态的最大轴尺度和 `lod_bias` 调整，再取有序并集；每级拼接该预算下各部件应选的原索引，保留骨骼、材质和顶点，不重新简化。公式依据 [Forward+ 正交选级源码](https://github.com/godotengine/godot/blob/4.6.3-stable/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp#L1071)及[模型尺度计算](https://github.com/godotengine/godot/blob/4.6.3-stable/servers/rendering/renderer_geometry_instance.cpp#L67)。本游戏正交视图的距离项为 1；透视镜头合并前后 AABB 距离不同，不承诺完全等价。转换器拒绝影响有 LOD 部件的动态缩放轨，并逐姿态核查相对尺度；弓弦虽有缩放轨，但本身没有 LOD。

### 原生图元计数的陷阱

Godot 4.6.3 Forward+ 的[有 LOD 计数分支](https://github.com/godotengine/godot/blob/4.6.3-stable/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp#L1093)累加所选级别的索引对应图元数，没有乘 `instance_count`；下面无 LOD 分支才乘该数。因此 MultiMesh 使用 LOD 时，reported primitives 会漏掉实例倍数，不能凭此计数骤降宣称实际三角形或 GPU 工作等量下降。旧测量值保留为原生报告值；后续批量候选需结合实例数量、选级索引及实际渲染计时解释。

MultiMesh 同一批次使用 GeometryInstance 的尺度选级，不独立读取每个子实例尺度。常态模型与有 LOD 部件尺度为 1 时可保持相同预算；尸体缩小等情况下不能声称逐实例选级完全一致，批次 AABB 也改变剔除粒度。

# 积木争霸 0.12：中继发送积压与逐事件刷新

本地三个独立原生 DTLS 进程复现了一个明确的丢包机制：中继收到并完整解码 144 个快照，只有循环末尾刷新时接收端仅收到 8 个；每次处理完接收事件立即刷新时收到全部 144 个。后一方案保留完整解码，只改变发送时机。此次结果支持这一中继补丁；公网七人对局和最终发行运行时仍需另外验收。

| 指标 | 循环末尾刷新 `end` | 每个接收事件后刷新 `each` |
|---|---:|---:|
| 中继收到的快照 | 144 / 144 | 144 / 144 |
| 接收端收到的快照 | **8 / 144，失败** | **144 / 144，通过** |
| 缺失快照 | 136 | 0 |
| 已有转发待发、service 返回接收事件却无原生发送的次数 | 143 | 0 |
| 未观察到原生发送期间累计的最大转发数据 | 2,053,854 B / 140 包 | 14,680 B / 1 包 |
| 中继完整解码累计墙钟时间（147 次，含控制消息） | 1,132.183 ms | 1,146.274 ms |
| 显式 flush 累计墙钟时间 | 0.062 ms | 22.922 ms |
| 最长中继 process 回调 | 1,169.895 ms | 1,187.303 ms |
| 接收端原生缓冲区警告 | 有 | 无 |

`end` 的接收端原始 stderr 共 10,024 字节，包含原生 `Buffer full, dropping packets!` 警告，位置为 `core/io/packet_peer_udp.cpp:318`。这是应保留的失败证据。六个进程退出码均为 0，只表示初始化、解码和序号等脚本断言没有失败；缺失包由夹具记录而非触发退出码，因此不能把 `end` 写成通过。其他五份 stderr 均为空。

原生机制与补丁

Godot 4.7.2 携带的 ENet 在 `enet_host_service` 开头先分发已排队事件，拿到事件后可以立即返回；这条分支在真正发送待发数据之前。分发器仍有后续接收事件时会重新排队该 peer。因此，不断调用 `service(0)` 不保证每次都处理待发网络数据。`enet_host_flush` 则直接调用原生发送函数。[service 源码](https://github.com/godotengine/godot/blob/4.7.2-stable/thirdparty/enet/protocol.c#L1633-L1667)、[事件分发源码](https://github.com/godotengine/godot/blob/4.7.2-stable/thirdparty/enet/protocol.c#L54-L107)、[flush 源码](https://github.com/godotengine/godot/blob/4.7.2-stable/thirdparty/enet/protocol.c#L1588-L1599)。

夹具在每次原生 service 后读取 `HOST_TOTAL_SENT_DATA`，有发送增量或显式 flush 就重置待发统计。因此表中约 2 MB 是**未观察到原生发送的连续区段**，并非简单把整帧数据相加。队列清空后，后续 service 本身也可以发送，所以不声称发送只发生在显式末尾 flush；这也解释了 `end` 的显式 flush 计时很短。

已检查产品 `server/relay_server.gd` 的差异：仅增加四行说明和 `connection.flush()`，位置紧接 `EVENT_RECEIVE` 中的 `_receive(...)`，现有循环末尾刷新保留。完整解码、身份与房间检查、频道校验、限流和线协议保持原样。没有新增节点，没有绕开校验，也没有更换传输可靠性。

验证方法与边界

这是一组顺序执行的本地对照，每组为发送端、中继、接收端三个独立 Godot 4.7.2 Windows 编辑器运行时进程，使用原生 ENet/DTLS 和临时自签名证书。每包包含固定种子的 500 个合成单位字段，压缩后平均约 14.67 KB。发送端到中继使用可靠消息，确保上游丢包不混入本次归因；中继到接收端使用快照的 `FLAG_UNRELIABLE_FRAGMENT`。中继和接收端均调用冻结自 `eca8ff9` 的实际 `NetworkProtocol.decode`，保留解压、JSON 解析和递归基本类型检查。两组每包时间戳引入极小的压缩尺寸差异。

中继循环上限为 512 个事件，帧率上限 30；发送与接收端上限 240，发送间隔至少 5 ms。没有用额外阻塞 sleep 人为加重中继，积压来自完整解码工作。这是高于稳定处理能力的有界突发机制验证，**不是 500 单位真实 Game、公网房间完整权限测试或发行模板性能测试**；不能据此宣称七人 15 Hz 或 60 FPS 已达标。

逐条刷新没有解决完整解码的 CPU 成本，最长回调仍约 1.18 秒。接收时间数组只统计成功收到的包，且使用同机墙钟；`end` 丢失 136 个样本，直接比较两组平均延迟会有幸存样本偏差，因此不将平均延迟作为收益结论。

原始计数、接收序号缺失列表、逐包大小、收到包的延迟、最长回调、文件指纹和失败日志摘要已保存在 [JSON 证据](release-0.12-relay-flush.json)。本地原始证据位于 `.local/release-0.12-relay-flush-proof`；测试脚本、临时证书与私钥不进入仓库。测试结束时命令核实六个辅助进程均已退出，仅用户编辑器 PID 36624 保留。此次归档不包含服务器部署，公网部署由后续发布步骤执行。

# 积木争霸 0.11.0.1：持续断线修复与中继扩容

日期：2026-09-10。此热修不包含正在开发的共享流场或静态移动实验，也不表示896单位性能已解决。

## 已复现的根因

用户反馈开局约20秒后显示“未能在重连时限内恢复连接”。本机两次实际2v2日志分别在约34秒、逻辑步1020/1024结束，过程中帧率正常；上海服务保持同一PID、零重启，无OOM记录。

使用未修改的正式PCK、Godot4.6.3、独立本机Godot4.7.2 DTLS中继，运行两真人加两个正常Bot的真实`main.tscn`，复现了同一故障：房主第35.385秒、逻辑步1021收到第12条`inactive_recipient`后进入error。服务器踢人时距最近收包仅3毫秒，明确不是心跳静默。

错误链路如下：

1. Bot与玩家共享生产、建造和命令入口；出兵完成、建成或命令失败时都会调用`notify_owner`。
2. 旧通知入口把Bot也当作远程UI接收者，给不存在的客户端发送提示。
3. Relay将每条消息记为`inactive_recipient`违规；累计12次断开房主，客人随之等待房主恢复。
4. 旧结果界面对所有连接error统一显示“重连时限”，掩盖了真实拒绝码。

此前191项发行检查涵盖握手、资源和短房间生命周期，没有运行足够长的真实Bot对局，因而漏检。此报告不将这些检查数量当作独立的持续对战场景数量。

## 修复边界

- 通知入口只给当前真人控制者投递UI消息；Bot正常生产和命令处理不受影响。
- `RelayClient`拒绝给电脑/空位发送快照或定向事件。资格来自房间席位，区别于当前模拟控制者，避免真人临时被Bot接管后无法接回。
- Relay对有效房主发给Bot的严格、有限长度UI notice执行无投递处理，允许已发行的协议10客户端继续运行。消息不转发、不广播、不累计违规；不放宽非法快照、空位、伪造身份、保留事件、频道、大小或总流量校验。
- 客户端保留真实错误码与简短消息；只有真正的`reconnect_expired`才显示重连超时。
- 双端补充脱敏诊断：连接状态、错误码、时间和有限计数；不记录地址、房间邀请码、token、玩家名字或消息正文。Relay日志具有速率上限。

## 中继容量

一个UDP端口可承载多个ENet连接。原来同时存在“最多1房”和“原生16个peer”两道限制，增开端口并不能直接解决房间配置上限。[Godot ENetConnection官方接口](https://docs.godotengine.org/en/4.6/classes/class_enetconnection.html)

现在默认8房×每房8名真人，64个在房真人席位；原生连接池80，额外16个供握手、重连和无房连接。无房大厅连接也会占用peer。房数支持1～16，池大小随配置计算；玩家编号和频道仍局限于单房，不能跨房消费或转发状态。

配置在服务启动时读取，扩容需要一次重启，不宣称无损热更新。仍使用UDP24571，其他应用UDP24570不变。容量验证与满负荷真实战斗带宽压测是不同范围，不能由64条轻量连接推断64人同时满人口对战吞吐。

各持续对局结束后，房间及会话均归零。公网测试仅按自己房间内部流水号1关联生命周期和两条peer退出事件；退出事件确认`rooms=0/sessions=0/strikes=0`，不将结束事件发生前的计数误当清理结果。公网RTT均值房主22.57ms/客端33ms，P95为29/33ms。

新包两组稳定期结束后才人为触发`diagnostic_rejection`，验证真实HUD正确显示协议拒绝码、没有误报重连时限；同名JSON保留这些预期诊断错误，稳定期内没有真实错误。65连接测试中的11次拒绝来自主动越界/伪造/畸形消息检查，属于预期结果。

持续对局用原生4.6.3引擎加载正式PCK，启用editor特性仅为允许外部诊断SceneTree入口；实际Game、RelayClient、地图和单位均来自对应PCK，未覆盖生产脚本。这和实际release EXE目录验收分别记录。此次没有重新验证896单位吞吐、64个完整游戏客户端或持续数小时对局。

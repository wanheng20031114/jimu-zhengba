# 积木争霸 0.11.0 性能实测与归因

**标准 272 单位样本保持约 30 TPS；896 单位的满人口性能问题仍未解决。** 最终样本平均分别为 **130.797 FPS** 和 **3.306 FPS**。后者的实际逻辑频率只有 **25.386 TPS**，画面明显卡顿，不能宣称本版解决了八人满人口战斗。

本报告将最终发布模板采样、开发过程中的诊断实验、历史版本分别归档。完整的紧凑数据、分布、查询次数、检查结果和源码 SHA-256 见 [performance-0.11.0.json](performance-0.11.0.json)。没有将每帧的大量 monitor 日志、机器绝对路径或连接凭据加入报告。

## 最终样本

使用 **Godot 4.6.3 官方 Windows release 模板**、生产 `scenes/main.tscn` 和生产单位脚本。临时入口只负责布置压力场景、收集顶层计时与结束；没有逐单位性能 wrapper，也没有使用自编译诊断引擎发布游戏。

| 场景 | 平均 FPS | 实际 TPS | 显示帧均值 | 显示帧 P95 / P99 | SceneTree 回调均值 | SceneTree 回调 P95 / P99 |
|---|---:|---:|---:|---:|---:|---:|
| 192 军事单位 + 80 农民，共 272 | 130.797 | 29.999 | 7.645 ms | 14.896 / 17.696 ms | 5.865 ms | 8.061 / 9.761 ms |
| 800 军事单位 + 96 农民，共 896 | 3.306 | 25.386 | 302.523 ms | 346.321 / 347.524 ms | 21.539 ms | 27.729 / 28.906 ms |

272 单位这次显示帧 P95 低于 16.7 ms，但 P99 超过这一界限，且仅为短时共享机器采样，不能据此保证所有实际对局稳定 60 FPS。896 单位连配置的 30 TPS 也未达到，仍不适合以最大人口聚集作为流畅体验的保证。

### 条件与样本范围

- Windows，Intel Core i9-10900KF，NVIDIA RTX 3080；Forward+／Vulkan，1600×900。关闭垂直同步及帧率上限，保留 TAA、MSAA 设置值 2、4096 阴影图集和物理插值。用户编辑器和另一游戏实例保留，工作站没有隔离给基准独占。
- 原生 4v4 地图、八位独立所有者、出生建筑、真实单位模型、音效、迷雾、采矿、移动、攻击与导航保持运行。每阶段预热 6 秒，再采样约 15 秒。
- 为维持声明的人口，基准将单位生命乘以 100，暂停 Bot 与自然金币增长，避免扩军。**这是压力夹具，不是发布版数值，也不是完整 Bot 对局或八客户端联网负载。**
- 标准档每人 10 剑士、6 弓手、4 骑士、2 投石车、2 加农炮及 10 农民。最大档每人完成军事人口与农民上限科技后，生成 50 剑士、50 弓手及 12 农民，达到 100 军事人口上限；它不是 800 辆攻城器的最坏模型组合。
- 镜头固定在中央，正交尺寸 58。四条原生战线都在模拟，不代表全部单位同时位于视口和己方视野内。标准档可见单位由 131 到 124，最大档由 446 到 359。

### 正确理解计时

`frame_ms` 是两次显示帧之间的**墙钟间隔**，包含追帧、引擎工作与系统调度，不是 GPU 绘制时间。`physics_logic_ms` 由 SceneTree 中的优先级标记夹住节点物理回调，未覆盖标记外的全部导航、PhysicsServer 和变换维护。因此最大档的回调 P95 为 27.729 ms，并不能证明完整物理步达到了 33.3 ms 预算；实际 TPS 25.386 已说明总体未达标。

最大档还记录了 **334 个同一显示帧内连续物理回调入口之间的间隔**，平均 33.300 ms。这些墙钟区间跨越上一步尾部与下一步准备，帮助观察追帧；它们不是逐步完整引擎 P95。384 个逻辑步只产生了 50 个显示帧，平均每帧约 7.68 步，仍有明显集中追帧。

最终 release 样本的 GPU、渲染提交 CPU 分布**没有采到数据**：源文件写出的 `samples=0` 与全零统计是空分布占位。本归档把这些统计改为 `null`，不解释为 GPU 或渲染成本等于零。

Godot 的 `Performance` 物理、导航、process monitor 是缓存读数；其中物理时间是低频更新的峰值，并非每次读取都测了一个新物理步。JSON 保留它们供追溯，但本报告不将其分布称为真实逐步均值或 P95。

## CPU／GPU 诊断证据

以下都是**非最终诊断快照**。早期样本使用官方编辑器引擎与临时 wrapper；正式样本使用 release 模板。各次战斗状态、异步导航发布时间与随机数消耗也可能不同，不把两次 FPS 差额全部归因于单项改动。

| 896 单位诊断 | FPS | 实际 TPS | 显示帧 P95 | SceneTree 回调均值 | GPU 均值 |
|---|---:|---:|---:|---:|---:|
| 早期 baseline，3D 开启 | 1.688 | 13.506 | 616.048 ms | 49.573 ms | 10.422 ms |
| 同阶段 no3d，关闭视口 3D | 1.676 | 13.412 | 626.407 ms | 50.048 ms | 0.972 ms |
| 中间阶段 whole_callback | 2.325 | 18.602 | 453.494 ms | 30.965 ms | 10.581 ms |
| 中间 release_plain | 3.323 | 25.523 | 337.131 ms | 22.536 ms | 未采样 |
| 中间 release_noanim，全单位动画关闭 | 8.408 | 29.726 | 209.269 ms | 15.654 ms | 未采样 |

关闭 3D 后，GPU 均值从约 10.4 ms 降到 0.97 ms，帧率仍约 1.7 FPS，回调时间仍约 50 ms。这个消融强烈支持**当时 896 单位样本主要受 CPU 工作限制**，并非单纯因为粒子或显卡画不动。它不证明其他镜头、分辨率或未来 CPU 优化后的场景没有 GPU 瓶颈。

`whole_callback` 为此前遗漏的移动回调补充了计时：280 个权威步中，全体单位的移动回调累计 2,124.352 ms，折合**每步 7.587 ms**；其中 `move_and_slide()` 累计 1,236.065 ms，折合**每步 4.415 ms**。这是全场总成本，后者包含在前者之内，不能相加，也不能把这部分全叫作 RVO 求解器成本。

全动画关闭实验说明动画、变换和与之相连的工作值得继续分析，但不能把 3.323 到 8.408 FPS 的差额全部归于 AnimationPlayer：这两次查询量分别为每步 14.185 与 6.826，战场进程也不同；关闭所有动画会改变出手姿态和武器挂点。**发布版没有关闭所有单位动画**，只对视口外或迷雾隐藏的动画自动更新休眠，并按权威时钟补齐姿态。

### 引擎级分段诊断

另使用官方 4.6.3 源码构建了临时 MSVC 优化计时引擎，仅作归因。完整窗口筛选、26 项计时字段与原始整数计数见 [原生阶段报告](performance-native-0.11.0.md)及其 [JSON](performance-native-0.11.0.json)。

保留的 5 个完整窗口涵盖 240 个物理步，完整物理步平均 42.211 ms。其中 SceneTree 节点物理回调平均 30.465 ms，Navigation3D 平均 8.260 ms，Jolt 的 `end_sync()` 与服务器 `step()` 合计约 0.563 ms。

这些边界必须保留：SceneTree 回调属于完整 SceneTree；Navigation3D 包含地图同步、避让与安全速度回调，也包含移动代码；角色的 `move_and_slide()` 不在 Jolt 服务器步进这 0.563 ms 内。完整父阶段和子阶段不能重复相加。原生窗口与脚本标记采样区间不同，也不能用两者均值相减来精确归因某个函数。

**该诊断捕获了后来撤回的 10 Hz 战斗决策实验，编译器也与发行引擎不同，不能当作最终发布 FPS。** 最终保持 30 TPS 权威模拟，没有把降低全军决策频率当作性能修复交付。

## 本版实际保留的优化

### 弹丸、特效与资源复用

原生 `projectile_pool.tscn` 预放置 **64 个弹丸模型**，繁忙时每批增加 16 个，视觉上限 **256**。飞行与伤害使用同一个 `ProjectileFlight` 内核，初始复用 64 份记录，空闲缓存上限 1,024，活动逻辑弹丸不受这个缓存上限限制。超过视觉容量会省略部分模型与尾迹，**不会漏掉命中或伤害**。发射者死亡、目标释放、暂停、结束对局和回调重入都使用统一生命周期清理。

保留 **128 个原生特效实例**。小火花、碎屑和尘土按屏幕 64 像素格、100 ms 时间窗合并，视口外的小效果不借用实例。爆炸、坍塌和指令反馈绕过这层过滤，容量紧张时优先替换小效果。装饰粒子与弹丸尾迹不再投射阴影，模型和建筑阴影保留。

声音独立于视觉池，延续原生有界声部：6 个 UI、24 个战斗、8 个环境动作声部，带类别响度、限流与优先级。视觉回收不截断声尾；没有背景音乐。这些声音池属于已有设计，不把它们全部列为本版新收益。

网格、材质、采样音频继续共享原生资源，阵营颜色用实例参数，减少重复实例化与资源副本。**共享资源和对象池不等于所有物体只有一次 draw call**，透明粒子仍有处理与绘制成本。本版没有未经测量就把现有粒子全换成 GPU 粒子。

### 迷雾与小地图

迷雾将每个视野圆转换为逐行区间端点，再用差分前缀累加一次得到各行覆盖，减少多个单位重叠视野反复访问同一格。视野刷新周期及同队规则保持不变。己方显示继续使用复用的 R8 `ImageTexture`。

小地图由原生 `TextureRect` 和 shader 读取同一张本地迷雾纹理，替代每显示帧最多 9,216 次脚本矩形绘制。地形探索与实体可见性规则不变，敌军实时数据仍经过房主过滤；不是用全图显示换取性能。

### 导航与近距离追击

保留原生导航区域、`NavigationAgent3D`、RVO 和预算内 A*。可通行单元合并为较大的凸矩形，并在共享边交点拆边，减少导航多边形数量；首三个顶点明确构成非共线转角，避免原生投影退化。

建筑和地图障碍生成阻塞前缀表。20 世界单位内的直接追击先用 O(1) 包围矩形查询；矩形命中障碍时，再沿路径逐行检查按单位半径扩大的扫掠区间。路径旁边的障碍不再让整片包围矩形一律回退 A*，但真正穿过障碍仍拒绝直行。新增工地及时更新占地，导航重建未发布期间也不允许穿越它。原有绕障与拥堵避让继续运行。

### 视口外动画休眠

每种可编辑单位 rig 使用 `VisibleOnScreenNotifier3D`。视口外或被迷雾隐藏时，两个原生 AnimationPlayer 的自动回调进入 `PROCESS_MODE_DISABLED`；重新可见时按暂停修正后的物理时钟恢复姿态与插值。

这里休眠的是动画表现，**单位移动、采矿、攻击冷却、伤害和网络权威模拟持续运行**。发射前显式采样原生攻击姿态与移动父变换，保证离屏弓箭和炮弹仍使用正确武器挂点。客户端快照动画保留自己的手动时钟，不叠加本地权威时间。预览、单位美术质量和可见单位的攻击动作不通过一律停播来换帧率。

## 历史对照与未完成目标

[0.10.0 历史样本](performance-0.10.0.md)中，272 单位为 74.40 FPS，896 单位约 1.90 FPS。这次最终分别为 130.80 与 3.31 FPS，但前次用编辑器引擎、本次用 release 模板，后台活动不同，场景随机进程也不是逐帧配对；不能将全部差额归因于本轮代码，更不能把它包装成严格的单项加速比。

本版减少了重复表现创建、迷雾绘制、导航保守回退和不可见动画更新，保留了操作与伤害语义。最终证据仍显示最大人口时 CPU 模拟、移动与场景回调有大量工作，并伴随集中追帧。接下来需要在**相同发行引擎、相同战斗状态**下分别测量这些范围，继续减少每单位重复查询与原生节点回调，再判断更大规模的模型或导航架构调整是否值得采用。这里是尚需完成的工作，没有把诊断实验算成已发布优化，也没有把 896 单位性能目标标为通过。

# 0.12 中继限流修复、兼容性验证与部署记录

日期：2026-09-10。对应[脱敏数据与源码哈希](release-0.12-network.json)。代码阶段提交：`77525c7`、`fffe90a`。

**旧七人对局的“超过发送上限”已有直接日志证据，限流结构已修复并部署；本地原生网络验证 2371 项、原有通用入口 98 项通过。后续七个真实 Game、同一世界 500 单位的公网压力测试未通过，出现传输断开与长快照空窗，不能宣称大规模联网性能已解决。**

## 旧版本断线的确定原因

旧服务日志在 UTC `2026-09-10 13:24:50.479077`（北京时间 21:24:50）记录七个真人席位的房主被 `rate_limit` 立即终止：窗口第 **401** 包，累计 **1,375,417 B**，最后一包位于快照频道 7，压缩后 **8,055 B**、解码长度 **70,319 B**。字节数远未到原来的 12 MiB 限额，触发的是原有每秒 400 包的硬窗口。此前 90 分钟的完整查询没有被条数上限截断。

这证明了直接踢连接的条件，不能反推全部 401 包的组成。旧日志没有正常包的分类计数；可靠包积压、服务端处理一批事件时复用旧时间戳均可能影响短窗口，历史证据不足以确定各自贡献。正常六名远端的 15 Hz 快照加 15 Hz 表现批次只有约 180 包/秒，因此本报告不把该事件描述为“正常发送器每步无限拆包”。它也没有解释所有 CPU 卡顿。

## 本次结构修改

- 房主总入口采用按实际真人接收者数计算的令牌桶：每秒 `170 + 70 × 其他真人席位` 包，允许 3 秒突发。七人房为 **590/s、1770 突发**；八人房为 **660/s、1980 突发**。暂时断线的真人席位保留预算，Bot、空位不增加预算；普通连接为 **200/s、600 突发**。角色、房间状态切换保留已消耗额度，不能反复离开／开始对局领取新突发。
- 170 的组成是控制 120、广播表现 20、广播关键事件 30；每接收者 70 是快照 20、表现 20、关键事件 30。生产完成、建成与常见操作反馈是可恢复的 `notice`，超过通知预算只丢提示并计数；死亡、攻击、弹丸、声音使用表现批次，正式结算使用独立控制消息。非法身份、载荷或保留事件仍拒绝，其他关键事件不会被悄悄当作表现丢弃。
- 解压前另计压缩字节与声明的解码长度。房主分别为 **12 MiB/s、96 MiB/s**，普通连接为 **2 MiB/s、4 MiB/s**，均为 3 秒突发。既有单包、频道及 primitive 深度／规模限制保留，令牌不是无限内存许可。
- 表现与关键事件改为按接收者各自计额，分别 **20/s、突发 60** 和 **30/s、突发 90**，广播单独计额。合法表现过量会在遍历事件数组前低成本丢弃；畸形或越权包仍按既有规则处理。
- 主循环每个原生事件重新读取单调时间，避免整批解码、验证时间都记入循环开始时的同一个窗口。
- 快照／事件经过身份、房间 epoch、目标、频道、序号和载荷校验后直接转发原始 ACN1 帧，省掉服务器重新 JSON 与 Zstd 编码。命令仍由中继重写可信 owner，不能靠原包转发伪造发送者。保留的路由 `to` 字段由旧客户端正常忽略。
- 客户端同接收者的表现批次受 50 ms 墙钟间隔约束，`ERR_BUSY` 交由原表现队列保留与过期机制处理。每约 5 秒输出有界分类计数，区分入口流量、转发与软丢弃；这些应用计数不冒充网卡吞吐。

## 验证范围与结果

新夹具使用一个 Godot **4.7.2** 无头进程中的九个独立原生 ENet/DTLS 端点，临时证书、本地端口和第二个隔离房间。没有连接公网，也没有实例化 896 个游戏单位。

| 验证 | 七个真人席位 | 八个真人席位 |
|---|---:|---:|
| 15 Hz 小载荷发送轮数／实测有效时长 | 48 / 3200 ms | 48 / 3205 ms |
| 成功转发快照／表现批次 | 288 / 288 | 336 / 336 |
| 3 秒合法可靠积压包 | 450 | 525 |
| 积压转发耗时／窗口峰值 | 53 ms / 558 包 | 72 ms / 559 包 |
| 独立 896 实体单包压缩／解码长度 | 4101 / 46027 B | 3382 / 46027 B |

**15 Hz 段只有 12 实体的小载荷；896 实体是另行单次真实路由检查。** 可靠积压在本地同时提交，不是公网丢包模拟。原生网络部分用实际墙钟，纯令牌边界检查使用显式单调时间。上述结果不能作为七人 500 单位持续带宽或游戏 FPS 结论。

2371 项断言包含 58 个不同标签，覆盖原包逐字节相同、私有／广播收件边界、跨房 epoch、伪造房主／频道／序号、命令归属、Bot 通知兼容、过量发送隔离、字节与解码预算、角色切换不重领额度。其中一个实际接收者使用与正式 `v0.11.0.3` 完全相同的客户端源码，只在解码前加只读原包捕获，证明新中继原包路由可以被旧客户端处理。原四端测试最小更新新私有方法参数与预算断言，并显式指定其原先要测试的一房容量，最终 **98/98** 通过。

两个最终辅助进程都以 0 退出，标准错误为空，并通过进程命令核实已经退出。保留用户正常编辑器。早期测试夹具曾有类型推断错误、相对时钟导致约 13.5 Hz、896 大载荷九端点只能达到约 7 Hz，以及旧夹具依赖一房默认值的四项连锁失败；这些中间记录没有被包装成最终通过数据，修正范围和最终哈希保存在 JSON。

另一个独立队列回归确认 `ERR_BUSY` 时不推进上次发送 tick、不移除待发非过期事件，实际等待后仅发一次。它将底层发送替换为捕获端，属于队列语义验证，不计入上表原生 DTLS 吞吐。

## 后续七人 500 单位公网失败：尚未闭环

真实测试是七个 Game 进程观察**同一世界 500 单位**，不是 3500 个世界单位。此次压力测试客户端包 SHA256 为 `afd64d753aaff5834bc9660d2b1533e195f129de4f043bfcdf1d67fb558416df`。本节引用主验收的指标：房主约 **15.87 TPS**，客人实收快照约 **0.8～2.18 Hz**，快照最大空窗约 **3.9～9.9 秒**。后续独立的小规模七人真实 Game 验证通过，不能替代这次压力失败。

服务器在 UTC **15:33:36.210361** 与 **15:33:40.592647** 先记录房主 `transport_disconnect`，各自之前的短窗口只有 44／53 包、约 118／147 KB。新服务同一 PID、invocation 和重启数不变，整段 **rejected=0，快照／表现／通知软丢弃均为 0**。因此这两次断线不应继续归因于本次应用限流。之后出现的 DTLS `-30464` 分别晚约 133 ms／4 ms，先后关系不足以把后发握手诊断认定为最初故障。

UTC **15:44:13** 的只读系统检查发现当前 UDP24571 socket 累计 **5145 次接收丢包**；全系统 `Udp.RcvbufErrors=6891`、`InErrors=6891`、`SndbufErrors=0`。该 socket 属于本次部署后仍在运行的服务，所以可以确认当前 socket 生命周期内发生过接收队列溢出；**缺少压测前基线，不能将 5145 次全部归于本次 stress1**。网卡收发错误／丢弃计数为 0，`fq_codel` 丢包、overlimit 为 0，没有 Linux 限速 class，MTU 为 1500。

服务器实际为 Alibaba Cloud ECS，未找到可回放该时段的 sysstat 采样。应用接收字节计数不包含全部 ENet／DTLS 开销和未完成重组的数据，也不等于网卡公网出站；来宾网卡与 Linux 队列不能证明云控制面的公网带宽规格，因此本报告**没有假定 3 Mbps 或 5 Mbps 限额**。官方只读 API 将 `InternetMaxBandwidthOut` 定义为实例的公网出带宽值，但本次没有调用付费或修改接口。[阿里云 DescribeInstanceAttribute](https://www.alibabacloud.com/help/en/ecs/developer-reference/api-ecs-2014-05-26-describeinstanceattribute)

下一轮最小复现需要在相同真实 Game 压测前后记录该端口丢包增量、socket 实际接收内存上限、每秒网卡出入站、UDP 队列与服务 CPU；同时对齐房主／中继／客人的 ENet 发收计数、RTT、throttle 和墙钟快照频率。ENet 原生统计覆盖已收发数据；`pop_statistic` 会取值并清零，必须由一个采集者拥有，避免多个监控互相清账。[Godot 4.7.2 原生统计实现](https://github.com/godotengine/godot/blob/4.7.2-stable/modules/enet/enet_connection.cpp#L208)

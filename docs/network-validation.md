# 联网部署与验收

本文保存 0.6.0 的发布与负载记录；新版本见 [0.7.0 联网发布验收](network-validation-0.7.0.md)。

## 发布契约

本轮使用游戏版本 `0.6.0`、网络协议 `2`。42 项单位、建筑、科技和地图资源由 `tools/build_content_manifest.py` 生成内容清单，当前 SHA256 为：

```text
286abc7c071ae8e26a580d136f2974a20db5a2a1d2c8aea1710650b9122f608a
```

文本资源按 UTF-8、LF 规范化后计算指纹，二进制 `.res` 保持原字节；清单自身也固定 UTF-8、LF。这使 Windows 工作区、Git 的换行规范化和新克隆得到相同指纹。修改规则或地图后，先重建清单，再同时更新客户端和中继。客户端从清单原始字节计算 SHA256，服务端在进入房间前拒绝版本或指纹不一致的连接。

公开信任证书为 `scripts/network/relay_trust.crt`，公开连接设置为 `data/relay_endpoint.json`。部署私钥与管理凭据不进入 Git 或 Windows 发布包。原始证书、`data/*.json` 和 `scenes/maps/*_layout.json` 需显式纳入导出；原生资源允许由 Godot 转换为二进制并重映射。

## 中继边界

上海部署使用独立 `ashen-crown-relay.service`，监听 UDP 24571，默认同时容纳一个房间、最多四个真人。原有 UDP 24570 及其他服务保持原状；部署工具不会修改主机网络限速、云安全组或其他应用。服务端使用独立、校验过的 Godot 4.7.2 运行时，客户端保持 Godot 4.6.3。

最新部署版本为 `fbe783b025ab4cb0`，状态为 `active`，已携带本章的新清单、快照编码优化、可靠表现限流及原生拥塞参考修复；部署前后原 `bot-jump-relay.service` 的 PID 保持不变。最终只读审计确认远端清单与服务端代码和本地逐字节一致，新旧服务均为 `active/running`，分别持有 UDP 24571 和 24570，自动重启计数均为 0。生产中继继续运行，测试辅助进程单独清理。原生拥塞修复前的历史部署为 `caaad5e662bfc42f`。

中继管理邀请码、席位、队伍、Bot 配置和连接身份，不模拟战斗。房主执行 30 TPS 权威逻辑；指令归属由已认证连接绑定，序号重复的包不会进入 Game。每个收件人的私有数据和当前可见状态由房主筛选，客户端只接收自己的经济/队列、同盟及可见敌人。迷雾中的建筑只保留最后看到的静态记忆。

控制、可靠表现事件和不可靠快照使用独立 ENet 通道。房主到中继的快照进一步按收件人划分通道 2–5，避免不同玩家的序号互相淘汰；中继向每个客户端使用通道 2。快照发送保持每人 15 Hz，服务端以 20 Hz、容量 3 的令牌桶吸收网络聚簇。消息限制和身份校验始终生效；传输只解析有界 JSON 基础值，不解码 Object 或 Resource。

每局随机 `match_id` 隔离不同比赛，旧局在途事件、快照、命令和结算不会落入下一局。首次连接最多重试 20 秒；普通断线 10 秒后由 Bot 接管，120 秒内可恢复原席位。房主断线暂停对局，30 秒内恢复则继续，否则中止。可靠结算原子释放房间。

信任边界是房主的 `MatchReplication` 从有类型游戏状态逐字段构建的快照：只有 `RelayClient.snapshot_to` 使用 `NetworkProtocol.encode_snapshot`，先检查房主身份、对局、收件人和活动连接，再调用原生 JSON 与 Zstd，始终保留 128 KiB 大小上限。该入口不接收原始命令、事件或中继转发数据。普通 `encode` 与所有 `decode` 继续执行完整深度、总值数、字符串/键长度、有限数值与基础类型检查；客户端还执行具体快照 schema 校验。新增协议测试证实专用与通用编码字节完全一致，恶意深度、总量、长键/字符串及非房主调用仍被拒绝。

280 单位首次丢包行军测试暴露了可靠事件的固定 90 次/秒窗口问题：发送本来已是每收件人 15 Hz 单批次，可靠分片丢包后的集中递送仍可能超出窗口，导致表现事件被计为非法指令并累积断线。修复后脚步、马蹄、轮声及灰尘按 4 米网格、0.2 秒窗口合并；每批至多 16 项装饰表现，优先保留弹道及战斗表现，同收件人每两个模拟 tick 最多发一批。过期装饰及去重缓存随刷新清理，生命周期、结果和界面通知不进入该积压队列。

中继在完成身份、对局编号、基础值、消息结构、通道、128/32 KiB 和总 400 包/秒等检查后，分别应用视觉事件 60 次/秒、突发 90 次，以及关键事件 30 次/秒、突发 45 次的令牌桶。超额视觉仅计入 `dropped_visual_batches` 并丢弃表现；关键事件的拒绝及 12 次非法断线规则保留。精确接收时间推进测试覆盖 91 个视觉包后丢 1 个表现、持续超额视觉不新增 strike、关键 pause 可靠到达四端，以及视觉预算耗尽后畸形结构仍被拒绝。

为降低动态坐标长小数产生的分片，只对发送快照中 `p` 的各分量按 0.01 米取整、`yaw` 按 0.001 弧度取整，直接生成 GDScript float64 数组，避免再经 `Vector3` 引入 float32 长尾。Game 真实位置、命令坐标、伤害、生命、动画及模拟时间均保持原值，协议结构和迷雾规则不变。

| 动态 280 单位单份消息均值 | 完整精度 | 展示量化 |
|---|---:|---:|
| 解码后的 JSON | 68,530.63 B | 58,813.47 B |
| 压缩应用消息 | 10,088.97 B | **4,900.80 B** |

压缩消息缩小 **51.42%**；最大单轴位置误差 0.004999962 米，最大朝向误差 0.000482576 弧度，均在半个量化步长内。其他状态字段和权威变换保持不变，既有出入视野、插值及 schema 回归通过。更少分片可以提高丢包链路完整收到快照的概率，但高丢包和大军队仍可能降低有效更新频率，具体表现须以对应四端实测为准。

280 单位首次行军还暴露了独立的原生拥塞参考问题。诊断版保持完整 live 测试与原有时序，在两端每 50 毫秒记录 ENet 指标；`.local/network/live-local-402e6ca4` 显示房主上行在观测起点的 throttle 为 2，265–1331 毫秒期间为 0，1597 毫秒恢复 32；同期中继到三个客户端基本为 32。房主参考 RTT 为 17 毫秒、参考方差为 9，恢复时参考方差更新至 18。这证实首次负载变化会让旧延迟基线主动抑制上行快照，不能仅以本次其他断言通过而忽略首份状态的等待。

[Godot 的原生 API](https://docs.godotengine.org/en/4.6/classes/class_enetpacketpeer.html#class-enetpacketpeer-method-throttle-configure) 与[内置 ENet 实现](https://github.com/godotengine/godot/blob/4.6.3-stable/thirdparty/enet/peer.c)表明默认参考窗口为 5000 毫秒，可靠确认会逐次调整不可靠消息发送系数。中继在 `EVENT_CONNECT` 后改用 `throttle_configure(500, 4, 1)`，由原生可靠消息同步两端，避免改动连接握手校验；减速仍启用，应用的发送频率、字节与身份限制继续生效。协议回归新增了四个客户端的真实窗口值与服务端非零减速断言。

## 导出资源值回归

初版 57 项自检只证明资源存在及联网协议可用，没有验证资源中的生产列表。随后实际对局检查发现：导出后大本营和兵营仍有正确的 HP、路径与类型，但 `produces` 数组为空。因此这 57 项结果不能作为生产系统的完整验收。

独立 Godot 4.6.3 最小项目对比了六组资源：直接继承 `Resource` 或继承自定义资源，分别使用 `PackedStringArray = []`、`PackedStringArray = PackedStringArray()` 与仅声明类型。源码运行六组均保留 `farmer/archer`；实际导出 EXE 中，只有使用 `= []` 的两组丢失数组内容，其余四组正常，各组 HP 均为 3000。独立复现的导出与运行 stderr 均为空，排除了主项目旧缓存和继承结构作为必要触发条件。

这一结果与 Godot [官方问题 #116909](https://github.com/godotengine/godot/issues/116909) 及其[修复提案 #117266](https://github.com/godotengine/godot/pull/117266) 描述的带类型 PackedArray 默认值缓存问题吻合。项目按[官方导出属性示例](https://docs.godotengine.org/en/4.6/tutorials/scripting/gdscript/gdscript_exports.html#exporting-arrays)，将声明更正为 `@export var produces: PackedStringArray = PackedStringArray()`。

仅修改声明后，常规重导仍沿用了四项旧二进制资源。随后用 Godot 原生 `ResourceSaver` 重新保存大本营、兵营、军工厂和敌方城堡定义，保留全部数值，通过规范序列化产生新的资源摘要，让原生导出转换缓存按资源变化更新。此次文本序列化变化使旧清单 `c40e7f…` 更新为本章的 `286abc7c…`；新清单已同步中继，旧包会因指纹不符被拒绝进入房间。

更新后的 `--network-smoke` 增加 38 项真实资源值断言：八类建筑的完整生产列表与生命/护甲、各单位的生产归属、农民价格与训练周期、六组击杀次数、攻城加成和六级科技数值。自检总计 95 项，输出额外标记 `resource_value_checks: 38`；发布 EXE 也必须通过这些检查，文件存在或源码通过不再足以判定成功。

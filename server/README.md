# 积木争霸加密房间中继

中继只管理房间、连接身份和转发，不运行战斗。房主按 30 TPS 模拟，以每客户端 15 Hz 发送按视野筛选的快照；丢包时实收频率会降低，画面插值由游戏层负责。

客户端发行号为 `0.12.0`，网络兼容标识 `BUILD_ID=0.11.0`、协议 `10` 和内容清单保持不变。更新后的 Relay 同时服务原协议10发行包和0.12包；旧协议9包不能混用。0.12的接收预算与快照转发优化需要更新Relay后生效；客户端新增表现发送的墙钟频率保护。0.11.0.2的个人击杀统计仍通过现有可靠结束消息传递，正确计分要求房主和客户端均包含该修复，见 [击杀统计修复报告](../report/kill-statistics-0.11.0.2.md)。协议10包含电脑难度、八玩家、空位和多阵营。断线原因、持续对局复现及多房验证见 [联机热修报告](../report/network-hotfix-0.11.0.1.md)，此前版本对齐记录见 [稳定联机发布记录](../report/stable-release-multiplayer-2026-09-10.md)。

## 接口约定

`RelayClient` 是常驻 `Node`，允许暂停时继续收发。`owner_id` 由中继分配，房主恒为 0；玩家所有权与 `team_id` 分开。模式由 `NetworkProtocol.MODES` 统一定义：1v1 为两人；2v2 为四人；3v3、2v2v2 为六席；4v4 与乱战为八席。真人和 Bot 均计入参战人数，允许保留空位（例如 4v2）。团队人数不能超过模式上限，但无需相等；至少两个实际阵营、真人房主和全部真人准备才可开始。乱战每个 owner 独立阵营，服务端拒绝组队。房间 UI 与中继共同使用 `NetworkProtocol.room_start_error()`。

- `connect_relay(address, port=24571)` 后调用 `create_room(mode, nickname)` 或 `join_room(code, nickname)`；握手未完成时创建/加入意图保留。
- 房主 `configure_slot(owner, kind, team, bot_difficulty)` 设置空位/电脑、队伍及电脑难度，不能覆盖真人。难度为 `normal/hard/very_hard/nightmare`，采集收益为1/2/3/4倍；非电脑席位只能使用 `normal`。变更清除其他真人准备状态，房间视图及开局配置均保留难度。真人 `set_ready(true)`，房主 `start_match()`；人数、准备状态、协议版本、游戏版本和内容清单 SHA256 均需一致。此配置使用协议10，需同步更新中继与客户端。
- `match_started(config)` 仅首次进入对局触发。配置包含 `mode/map_id/match_id/seed/host_owner/players`，地图 ID 分别为 `duel`、`teams`、`trios`、`triad`、`quad_teams`、`free_for_all`。
- `send_command(Dictionary)` → 房主 `command_received(owner, command)`。`owner` 来自已验证连接，游戏层仍须验证单位归属、资源、射程和可见目标，不能使用载荷自报的 owner。
- 房主 `snapshot_to(owner, snapshot)` → 指定玩家 `snapshot_received(snapshot)`；禁止快照广播。`send_event(owner, event)` 为可靠事件，`owner=-1` 仅适用于可公开的信息。
- `finish_match(result)` 仅房主可调用，`winner` 必须为该模式合法阵营或平局 `-1`，释放房间；`leave_room()` 退出席位；`disconnect_relay()` 完全断开。
- 重连不会重载世界。`connection_restored` 表示本机通道恢复；房主收到 `player_reconnected` 后必须向该玩家发送全量恢复状态，并结束对应 Bot 的控制。

通道 0 用于可靠指令/房间，通道 1 用于可靠事件；房主到中继的有序不可靠快照按收件人使用通道 2–9，中继到单个客户端则使用通道 2。独立的序号窗口避免后发给另一玩家的快照淘汰本玩家乱序到达的快照。消息仅接受 JSON 基础值，向量须转成数组；不反序列化 Godot Object/Resource。每指令 4 KiB、每事件 32 KiB、每快照 512 KiB、嵌套 12 层、最多 65536 个基础值；100 指令/秒、每目标最多 20 快照/秒，附带总包数及总字节上限。快照允许 ENet 不可靠分片：丢片会丢弃旧快照，不阻塞可靠命令。游戏应优先发送紧凑字段和变化数据，512 KiB 是防护上限，不是带宽预算。客户端最多接收 1536 个可见单位／建筑实体，为八人各 100 军事人口和 12 农民之外的建筑、工地留出空间。

512 字节以上消息使用 Godot 原生 Zstd 整包压缩。固定 ACN1 帧头携带解压长度与压缩标记；接收端先核实长度上限和发送权限，再分配有界缓冲并解析基础值。每通道大小限制按解压后内容判断，压缩不会绕过指令上限；未压缩的小消息保留相同帧头。

服务端按收件人使用 20 Hz 持续速率、容量 3 的快照令牌桶，吸收网络抖动造成的短暂聚簇；不以相邻到达间隔判定频率，避免额外丢弃合法 15 Hz 更新。客户端发送频率、单包大小和全连接字节上限仍同时生效。较长积压只保留有额度的快照，其余软丢并计数，不让旧位置阻塞新的可靠命令。

0.12在接收时先验证连接身份、通道与解压长度，再有界解析原始JSON，验证对局epoch、收件人及快照序号。通过后按原始ACN1字节转发，不再次JSON序列化或Zstd压缩。接收端通道仍为2；保留的`to`只是路由字段，原协议10客户端正常忽略它。可靠事件同样可以在验证后转发原帧，广播只遍历当前房间。玩家命令继续由Relay重建并写入已认证owner，绝不转发客户端自报身份。

全连接保护改为按实际真人收件人数计算的令牌桶。令`N`为当前房间房主以外的真人席位数（暂离保留席位仍计入，Bot和空位不计）：已认证对局房主每秒预算为`170 + 70×N`个包，容量为该速率的3倍。70由每目标快照20、表现20和关键事件30构成；基础170覆盖控制120及广播表现20、关键事件30。因此7真人为590包/秒、1770包突发；8真人为660包/秒、1980包突发。普通或未入局连接为200包/秒、600包突发，且不能发送快照。收件人数只在房间成员变化时更新，逐包读取为O(1)。

此外，在解压前独立计费：房主压缩流量12MiB/秒、声明解压流量96MiB/秒；普通连接分别2MiB/秒和4MiB/秒，均允许最多3秒积压。大厅、对局或席位变化只调整容量并保留已消费余额，不重发满桶额度，防止反复建房刷预算。声明尺寸随后仍须符合每通道及整包硬上限。所有包，包括无效包和旧局包，都消耗预算。持续超过预算的连接会拒绝并断开；合法积压不再因单秒第401个包被误踢。每个原生事件使用当下单调时钟，避免处理一整批512个包时将全部计入批首同一时刻。容量是保护上限，不代表已证明服务器能同时承载所有房间的最大吞吐。

每局具有独立的 128 位随机 `match_id`。指令、快照、事件和结算都携带该标记并由双方验证，旧局的在途包不会进入下一局。房间结束后会静默排空已有连接中延迟到达的战斗消息；未曾加入房间的连接仍不能发送权威消息。该标记用于对局隔离，不替代连接身份或重连 token。

内容清单由 `tools/build_content_manifest.py` 以 UTF-8、LF 生成：文本资源先规范换行，二进制资源保持原字节，避免 Git 换行转换改变同版指纹。更新规则或地图后须先重建清单再同步部署。量化结果与发布包流程见 [联网部署与验收](../docs/network-validation.md)。

完整的 `players` 数组始终保留所有席位索引。空位使用 `controller="open"`，不创建资产、金币、Bot、经济、视野或重连会话，也不参与胜负。真人断线后仍保留同一席位及 token，按原 10 秒 Bot 接管／120 秒重连规则处理；不可把暂离误认为空位。阵营出生区独立分配，稀疏 owner ID 不会让盟友跨阵营出生。

## 游戏状态复制

`scenes/match_replication.tscn` 保存独立的 `MatchReplication` 节点。对局用 `configure(game, relay)` 绑定，房主每个物理帧末调用 `tick(delta)`，客户端每个显示帧调用 `render(delta)`。房主每两个 30 TPS 模拟帧为每个客户端发送一次快照，最多七个收件人错开到两个发送相位（每步最多四个快照），降低单帧序列化峰值；既有单位、建筑与地图矿脉使用稳定的 `entity_id`。

每个收件人的快照含自己和盟友实体，以及当前可见的敌方实体。训练队列、学院研究、集结点、金币和升级状态只发给所属玩家；矿脉占槽数只在该位置可见时发送。战争迷雾只携带 Base64 地形网格，敌方单位和建筑离开视野后不发送当前状态，也不留下模型残影。接收层校验完整结构后再修改场景，也不允许网络实体覆盖地图矿脉 ID。

客户端以 120 毫秒缓冲平滑显示，位置线性插值、朝向走最短弧，攻击动作按房主发来的动画时间采样。原生 `AnimationPlayer.seek(..., update_only=true)` 不执行方法或音频轨；单位物理、避让、攻击计时器和生产逻辑均停用。客户端不预测伤害和经济，断包时停在最后已知位置。实体离开视野时静默释放，迷雾层只保留已探索地形；此操作不会调用阵亡、退款或死亡音效。可靠弹道、命中和音效由游戏事件路径单独处理。

可见的弹道、音效和命中交给 `queue_host_visual(owner, event)`，由复制层自动添加模拟时间并按 15 Hz 聚合为可靠 `visual_batch`，最多 96 条且不超过事件字节上限。客户端在同一展示时间线发出 `visual_event_due(event)`，游戏再播放表现，避免声音比攻击动作提前。每个收件人的表现积压最多 256 条；断线恢复跳到最新快照并保留已有实体，超过半秒的旧表现丢弃，不重放音效洪流。生命周期和界面通知使用普通可靠事件立即处理。

脚步、马蹄、轮声和灰尘使用 4 米网格、0.2 秒去重窗口，每批最多 16 条装饰项，投射物与战斗表现优先；过期装饰及短时缓存会清理。中继按收件人分别使用表现20次/秒、突发60次，以及关键事件30次/秒、突发90次令牌桶；广播另用一条同上限的独立桶，最多18个桶。八人房正常7×15=105次/秒表现不再争用全房100次/秒预算。表现额度耗尽时不再遍历批内条目，仅软丢并计数；解压、身份、epoch与基础JSON校验仍受前述硬预算约束。

客户端每收件人最多每50毫秒提交一次表现批次；物理追帧不会在同一显示帧重复压缩发送，`ERR_BUSY`交回复制层保留待发批次，过期项按现有规则删除。完整且有界的`notice`超过关键事件额度时仅丢该可选UI提示，不累计违规，避免同刻批量训练完成导致整局掉线。单位阵亡、弹丸、命中和音效属于表现批次；暂停属于普通可靠事件，其他关键事件仍保留超限拒绝。最终胜负走独立控制消息`finish`，不与表现或通知争用事件桶。

服务每约5秒输出一条有界`traffic`汇总：实际区间毫秒数、各通道收到的包/压缩字节/声明解压字节、转发快照/表现/关键事件/命令、快照/表现/通知软丢和拒绝计数。计数是区间总数，不能直接当作每秒速率；快照计数是成功提交原生发送，事件计数是已验证转发批次，不代表每个接收者实际收到。拒绝记录另含触发的预算类型及当前包速率/突发容量，不记录消息正文或玩家私密数据。

## 断线行为

首次建立加密连接遇到丢包时，在 20 秒总期限内重试，保留尚未提交的创建/加入房间意图；成功收到版本握手响应后结束首次连接期限。证书验证始终开启，失败不会降级到未加密传输。

房主断开后广播 `host_paused`，保留 30 秒；认证回连后 `host_resumed`，超时 `match_aborted`，不选举新房主。普通玩家断开广播 `player_disconnected`，10 秒后 `bot_takeover`，120 秒内可用内存中的 256 位随机 token 恢复原席位。主动退出立即由 Bot 接管。token 不出现在公开房间、日志或其他玩家消息中；重启应用后不保留 token。

## 部署与凭据

`python tools/deploy_relay.py --certificate` 初始化私钥及公开信任证书。私钥仅在忽略的 `.local/network/`；仓库只包含 `scripts/network/relay_trust.crt`。客户端使用受信证书及固定 TLS 身份 `jimu-zhengba-relay`，不关闭证书验证，也不要求公网域名。更换信任证书必须配合客户端更新，默认有效期三年。

`python tools/deploy_relay.py --deploy --max-rooms 8 --max-humans 8` 通过 Python 内存读取明确授权的 `shanghai` 凭据块，上传到独立 `/opt/jimu-zhengba-relay` 并启动 `jimu-zhengba-relay.service`。专用用户、只读系统目录和 384 MiB 内存上限；默认同时8房，每房最多8名真人，共64个真人席位。`max_humans`是每房上限。原生连接池为房数×每房人数+16，默认80；额外16个名额供握手、无房大厅连接和重连使用，无房连接仍占名额。房数支持1～16，更改后需要重启才能重建连接池，现有对局不会迁移。首次更名部署只停用本游戏之前的中继服务，失败时恢复它；其他应用的 UDP24570 服务保持原 PID。新服务仍只监听 UDP24571，无需为每间房开放新端口。云安全组需开放此端口，客户端网络须允许 UDP。

Bot没有UI接收连接。新客户端的通知入口只向真人发通知；发送API按房间席位身份校验接收者，不把临时Bot接管误判为永久电脑席位。为让已发行的协议10包继续使用，Relay对合法房主发向Bot的严格`{kind:"notice",text:非空且最多512字}`提示作无投递处理，不累计违规，也不广播；身份、频道、大小、频率校验保留，其他非法状态仍拒绝。服务端结构化诊断记录连接/房间生命周期、拒绝码和无投递计数，有全局日志速率上限；不记录邀请码、凭据、IP或消息正文。

服务端使用隔离、校验 SHA256 的官方 Godot 4.7.2 稳定运行时。客户端仍兼容项目当前 4.6.3；不修改用户安装。4.6.3 的 DTLS Cookie 析构具有上游已确认的重复释放诊断，服务端需使用包含 [Godot #120371](https://github.com/godotengine/godot/pull/120371) 的版本。原生 [ENetConnection](https://docs.godotengine.org/en/4.6/classes/class_enetconnection.html) 提供 DTLS 和独立通道传输。

### 正式中继导出包

正式运行使用官方 **4.7.2 release export template**。编辑器即使加 `--headless` 仍编入调试功能；Godot [专用服务器文档](https://docs.godotengine.org/en/4.6/tutorials/export/exporting_for_dedicated_servers.html) 推荐服务器使用导出模板。`server/relay_bootstrap.tscn` 是独立服务器主场景，Node 脚本负责唯一的配置与启动路径；旧 `--script server/relay_main.gd` 开发入口复用它，不维护第二套房间或配置逻辑。

`tools/build_relay_release.py` 只复制八份服务器必需源码/配置，使用官方编辑器导出 PCK，再原样复制校验过的 Linux/Windows release 模板。参数为 `--editor`、`--templates` 和 `--output`；首次可加 `--fetch-templates` 下载完整官方模板归档并按固定 SHA256 校验，再仅提取两个目标模板。模板缓存内的 `receipt.json` 与两份二进制是后续构建依赖；完整 `.tpz` 归档验证完成后可清理。

输出 `linux/jimu-relay`、`linux/jimu-relay.pck`、`linux/build-receipt.json`，Windows 对应 `jimu-relay.exe`。原生 release 模板禁用路径/脚本覆盖，所以可执行文件与 PCK 必须同目录同名，仅以 `jimu-relay --headless` 启动；配置继续从 `JIMU_RELAY_CONFIG` 读取，私钥不进入 PCK。部署应把二者上传至同一个不可变版本目录，保留旧版本和原 systemd 单元以便回退，不将新 PCK 覆盖到共享运行时旁边。

启动日志 `JIMU_RELAY_RUNTIME` 显示版本、editor/debug/dedicated_server 标志；正式模板应为 `false/false/true`。本地原生模板与 DTLS 验证范围见 [发行模板核查报告](../report/release-0.12-relay-release-runtime.md)。模板切换本身不改变协议或放宽 `Protocol.decode`，不能代替真实多人吞吐验证。

## 验证

0.12使用全新临时原生ENet/DTLS夹具验证7/8真人、合法积压、旧客户端原包兼容与伪造边界，另以实际`RelayClient`和复制层验证`ERR_BUSY`保留队列。下列通用本地运行入口继续保留，其限流断言同步更新为按收件人预算；本轮多人压力证据来自独立新夹具。

2026-09-10本地新夹具2371项通过：7/8个真人席位在约3.2秒中每端发送48轮，分别转发288/336个快照及同数表现批次；450/525个合法可靠积压包全部转发，窗口计数达到558/559也未被误踢。正式0.11.0.3客户端源码实际接收的快照/事件字节与原帧完全相同，私有收件人、跨房epoch、广播边界、伪造身份/通道/序号、角色切换不重领额度及过量发送隔离通过。该测试使用一个无头进程内的独立ENet/DTLS连接，15Hz阶段为12实体小载荷；896实体大载荷另作单次真实路由检查，不把它当作大规模持续带宽或游戏FPS证据。原四端通用脚本98项亦通过。

`tests/network_relay_test.gd` 使用真实本地 DTLS 四客户端，覆盖房间、版本、身份防伪、重复命令、分片快照、私有发送、可靠广播与断线时间边界。应在独立 4.7.2 测试项目运行，避免旧服务端析构缺陷。

可以直接运行 `python tests/network_runner.py local`，工具自动准备隔离项目与校验过的运行时；测试生成并删除自己的临时证书，不需要生产私钥。`remote` 执行公网四人压测，`certificate` 验证错误信任证书被拒、正确证书仍可连接；后者原生 TLS 拒绝诊断是预期的负向测试输出，任何脚本错误仍判失败。

`tests/network_remote_test.gd` 读取忽略的 `.local/network/endpoint.json`，使用项目当前运行时连接部署中继，创建四人房间并发送 280 单位快照；结束后主动释放房间。它不打印 endpoint、token 或消息正文。

`python tests/network_runner.py game` 在已导入的项目中实例化实际单位与建筑场景，验证视野过滤、经济隐私、稳定 ID、原生动画采样、断包冻结、消失与重新发现，以及 280 单位的序列化预算和各收件人 15 Hz 的交错发送。也可直接使用 `godot --headless --path . --script tests/network_game_replication_test.gd`。测试仅替换对局协调器与迷雾输入，不启动中继或改变生产服务。

`python tests/network_game_live_runner.py local` 启动临时独立中继与四个无头游戏进程，每个进程加载真实 `main.tscn`。测试自己的移动、训练、非法归属/金币/事件、共享视野、战争迷雾、普通断线后的 Bot 接管、房主暂停及双方重连，再由远程攻击指令验证实际伤害。临时证书、协调记录及日志均位于忽略的 `.local/network`；结束时关闭所有测试进程并删除临时私钥。`remote` 使用同样四进程场景连接已部署中继，结束释放测试房间。

`python tests/network_game_live_runner.py impaired --seed 24571 --loss 0.04` 在上述本地四进程之间加入独立 Python UDP 转发线程，默认往返基础延迟 150 毫秒、往返抖动范围 ±40 毫秒、4% 数据报丢包；`--loss` 可取 0.03、0.04 或 0.05。另有 8% 包增加 90 毫秒迟延以触发实际乱序。每个客户端入口和每次重连的上游 socket 均隔离，DTLS 字节不被解析或修改；不改变操作系统网络、云安全组或公网服务。配置是客户端到中继的链路往返值，房主到另一客户端的消息还需经过两段链路。

扰动报告保留固定随机种子、上下行包数/字节数/实际丢包率、实际乱序次数、递送延迟和正常对局阶段快照间隔的 P50/P95/最大值；默认加入 15 秒稳定观测段，可用 `--steady-seconds` 调整。主动断线测试不混入快照抖动统计。丢包和乱序从首次握手起生效。DTLS 对乱序握手的原生 `-30464` 拒绝诊断单独计数，只有有界重试最终完成全部对局断言才通过；证书验证失败、其他原生错误和所有脚本错误仍判失败。测试等待四端的可靠结算后才退出，并检查不存在计划外断线。

2026-09-09 的独立快照通道验收使用种子 24572、5% 丢包概率：87 项真实对局断言通过，4,921 个数据报实际丢失 238 个（4.836%）、实际乱序 846 次；三个远端累计 629 个正常快照间隔样本，P95 分别为 167/167/183 毫秒，最大值 283 毫秒。相比共用快照通道的同配置运行，原先受影响玩家的 P95 从 451 毫秒降至 167 毫秒。该结果是本机四进程、原生 DTLS 的网络扰动验收，不是公网延迟或渲染 FPS 基准；线程调度和包数会使重复运行的精确数值变化。

`python tests/network_runner.py expiry` 用实际 `main.tscn` 和 `RelayClient` 分别验证房主与普通玩家耗尽本机重连期限后，结束对局、释放暂停并显示中断结果。该测试明确把保存的单调时钟期限向前移动，不实际等待 30/120 秒，也不修改生产常量。`local` 传输测试另外核实服务端 10/30/120 秒原始值和边界前后的 Bot、席位释放及原子中止行为。

`python tests/network_release_runner.py <Windows发布exe路径>` 直接运行导出的程序及其 `--network-smoke` 入口，不要求发布包包含 `tests/`。保存的 `release_probe.tscn` 校验公开 endpoint、信任证书、完整内容清单及所有列举资源，并执行 38 项真实资源值断言（生产列表、单位归属、训练、击杀次数、攻城加成及科技），通过真实 DTLS 验证服务端接受该指纹，再创建临时房间、完成网络 start/finish 并确认释放。完整验收要求至少 95 项通过，旧版只有文件存在检查的包不能通过 runner。它不会载入 Game、生成单位或改动经济。原始 JSON 文件和公开 `.crt` 必须显式纳入导出过滤；原生资源使用 `ResourceLoader` 检查存在及实际属性值，以兼容导出后的二进制重映射。日志只含版本、指纹和检查结果，不输出地址、邀请码或重连 token。

部署脚本只负责本游戏服务，不更改云安全组或其他应用，也不安装 Web 服务。ENet 中继的全部游戏流量经过服务器，实际并发需按服务器公网带宽和压测结果确定。

历史 0.6.0 部署为 `fbe783b025ab4cb0`，协议 2、版本 0.6.0，42 项资源清单 SHA256 为 `286abc7c071ae8e26a580d136f2974a20db5a2a1d2c8aea1710650b9122f608a`。只读审计确认远端清单和服务端代码与本地一致，新服务持有 UDP 24571，旧服务仍持有 UDP 24570，均为 active/running、自动重启次数 0；部署前后旧服务 PID 未变。

中继在原生 `EVENT_CONNECT` 后设置 `throttle_configure(500, 4, 1)`，可靠同步两端，保留拥塞降速。它修复了默认 5 秒 RTT 参考在首次大规模负载变化时令房主快照发送系数持续归零的问题；不会绕过应用的 15 Hz 发送目标、消息大小、令牌桶和身份检查。原生协议 88/88、最终四端 280 单位本地及 4% 丢包各 118/118 通过。20 秒实测房主上传约 266–288 KB/s；高丢包下完整快照实收 7.3–7.7 Hz、最长间隔 622ms，因此不能把目标发送频率当作实际接收频率。精确字节边界、原生指标、性能长尾及可重复命令见 [联网验收文档](../docs/network-validation.md)。

## 六至八玩家模式验证

`python tests/network_runner.py multiplayer` 创建八个独立 ENet/DTLS 客户端，逐一验证各模式的真人和 Bot 配置、队伍人数、乱斗禁止组队、第五/第六收件人私有路由、绑定身份与重复命令过滤。

`python tests/network_game_live_runner.py local --mode 2v2v2` 运行六个实际主场景；`--mode 3v3` 和 `--mode ffa` 运行另两种模式。短流程覆盖开局塔、真实远程移动、资产权限、原始快照隐私、第六玩家 Bot 接管/认证重连、三方/乱斗中的单方淘汰与最终胜负。默认不带 `--mode` 仍运行原四端完整生产/研究回归，`--load-units 280` 仍只用于该四端压测。

`python tests/network_runner.py six-codec` 用原生场景作为模板，构建 896 单位、160 建筑、9216 迷雾格、本方 112 个单位各 9 项可见指令计划及满生产队列的 primitive 快照，验证 512 KiB/65536 值预算、owner7 私有科技及联盟不可变／淘汰布尔字段约束；敌方建筑记忆已移除。测试不生成 896 个单位场景，不把合成压缩字节当作实测网络吞吐。

`python tests/network_runner.py empty-slots` 载入真实 4v4 和八人乱战地图，验证 4v2、稀疏 owner ID、空位无资产/收入/视野、伪造空位状态拒绝及真实参战阵营胜负。`multiplayer` 套件运行八条原生 DTLS 连接，检查收件人 7 的独立快照通道、身份、重复指令和稀疏席位重连。
